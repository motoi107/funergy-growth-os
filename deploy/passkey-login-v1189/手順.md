- スタッフは、GM が「メール＋パスキー」にした人から、パスキー（指紋・顔）かメールのコードで入る。自分の端末は 12 時間ログインしたまま。
- GM・CEO・経理は今までどおりメールとパスワード（パスキーも足せる）。ほかの人は今までどおり PIN。
- v1183 の「ログインの試し」はやめる。

## 入れる前に（v1186 が入っていること）

`deploy/pin-off-v1186/` の ②（20261206＋20261207）が入っていること。① の 1 で分かります。

## 順番

1. **① `1_最初に確認_読むだけ.sql`**（読むだけ）。STOP が 1 つも無ければ次へ。
   - 3 が STOP：GM のメールのアカウントが社員と結ばれていません。Claude に。
   - 4：ログインの試しで使っている端末の数（2 で止まります。その人は今までどおり PIN）。
2. **Supabase のパスキーの設定**（Authentication の設定。画面の名前は Supabase の版で少し違うことがあります）
   - Passkeys（WebAuthn）を ON。
   - Relying Party ID：`funergy-plus.com`
   - 許可する origin：`https://funergy-plus.com`
   - 表示名：`Funergy+`
   - 新しい利用者の登録（Allow new users to sign up）が **OFF** であることを確かめる（ON のままでも動きますが、知らない人が利用者を作れます。GM・CEO・経理・業務Bot のアカウントは管理者が作るので OFF で困りません）。
3. **Google Cloud**（送り手のメールをつなぐため）
   - QuickBooks の Gmail（v1094）と同じ OAuth クライアントを使うなら：そのクライアントの「承認済みのリダイレクト URI」に `https://<プロジェクトの ref>.supabase.co/functions/v1/device-login` を足す。Secrets は今の `GMAIL_OAUTH_CLIENT_ID`・`GMAIL_OAUTH_CLIENT_SECRET` をそのまま使う。
   - 同意画面が「内部」のときは、送り手（GM の会社のメール）が同じ Google Workspace の人であること。違うときは別のクライアントを作り、Supabase の Secrets に `DL_MAIL_CLIENT_ID`・`DL_MAIL_CLIENT_SECRET` を入れる。
   - 使う許可は `openid`・`email`・`https://www.googleapis.com/auth/gmail.send` だけ（読む許可は使わない）。
4. **関数 device-login を入れる**（Claude が直接渡す非公開の 1 ファイル `device-login_v1189_index.ts`。リポジトリには置かない）。Edge Functions → **device-login** → Code に全部貼る → Deploy（Verify JWT は今のまま OFF）。SQL の前に入れても何も変わりません。
5. **② `2_SQL.sql`**（migration と同じ）。
   - 「STOP: 先に …」と出たら何も変わっていません。1 に戻る。
   - ここでログインの試しは止まります。まだだれも「メール＋パスキー」ではないので、ほかは何も変わりません。
6. **③ `3_確認_読むだけ.sql`**（読むだけ）。NG が 1 つも無ければ OK（11 は「まだ」で OK）。
7. **④ 送り手のメール**：`4_送り手_SQL.sql` をコピーして、`ここに送り手のメールアドレス` を GM の会社のメールに書き換えてから流す（アドレスはリポジトリ・GitHub に書かない）。最後に `sender_set` が true。
8. **マージ**（アプリ 1189）→ **全部の端末を 1189 に**（店のタブレットも）。アプリを開いて「更新」→ ログインの画面の版が 1189。
9. **GM が送り手をつなぐ**：PIN の一覧 →「ログインの方式」→「Google でつなぐ」→ 送り手のメールの Google アカウントで入って、許可をすべてチェック → アプリに戻ると「送り手のメールをつなぎました」。「ログインの方式」の上に「つながっています」。
10. **1 人で試す**（自分の電話を持っている人）：「ログインの方式」→ その人の「メール＋パスキーにする」→ メールと「本人に伝えた」→ 招待のメール → 本人がリンクを開く → コード →「自分だけが使う端末」と「パスキーを保存」→ 入れる → ログアウト → 一番上の「パスキーでログイン」で入れる → アプリを閉じて開くと、そのまま入っている（12 時間）。共有の端末では名前を選んでメールのコード。
11. 問題がなければ、ほかの人も同じように。

## 困ったとき

- **招待・コードのメールが届かない**：「ログインの方式」の上の送り手が「つながっています」か。切れていれば「Google でつなぐ」をもう一度。迷惑メールも見てもらう。
- **パスキーが使えない**（「この端末ではパスキーを使えませんでした」・「まだサーバーで使えるようになっていません」）：2 の設定（RP ID・origin）を確かめる。メールのコードでは入れます。
- **本人が電話をなくした・パスキーを消したい**：「ログインの方式」→ その人 →「ログインとパスキーを止める」（すべての端末）。本人は名前を選んでメールのコードで入り直し、パスキーを保存し直す。
- **PIN に戻す**（その人だけ）：「ログインの方式」→ その人 →「PIN に戻す」（新しい PIN を決めて本人に伝える）。
- **全部止める**：`止める.sql`。パスキーとメールのコードのログインを止め、メール＋パスキーにした人も前の PIN でまた入れる（PIN を忘れた人は GM が PIN の一覧で新しくする）。表と記録は残す。また始めるときは ② をもう一度。
- **関数を前（v1186）に戻すときは、先に `止める.sql`**。② が入ったまま関数だけ戻すと、メール＋パスキーにした人は PIN でもパスキーでも入れなくなります。

## 気をつけること

- **全部の端末を 1189 にしてから**「メール＋パスキーにする」。1188 以前のアプリでは、その人は PIN で入れず（メールとパスワードの段が出るが、その人のアカウントは無い）、パスキーの入口もありません。
- メール＋パスキーにした人は、その時から PIN では入れません（招待を済ませる前でも）。本人にメールを確かめてから押す（「本人に伝えた」のチェック）。
- 1 人に 1 つのメール。GM・CEO・経理・業務Bot のメールは使えません（「ほかのログインで使われている」）。
- GM・CEO・経理のアカウントはこの方式に入れません（メールとパスワードのまま。マイページで自分のパスキーを足せます）。
