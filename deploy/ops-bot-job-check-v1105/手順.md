# 業務Bot の「Job確認（16:30 基準）」を入れる（アプリ v1105・関数 ops-bot）

Moto さん 10/21 18:49 HST の依頼 ② → UI案60 → 回答（3 A・4「10/16 以降」・5 A・6 A・7 A・8 A）。仕様は `docs/LALA_JOB_CHECK_V1105_JA.md`。

- LaLa（F06）の通常 G1 は、打刻（Job の区間）の開始が **16:30 より前なら Prep、16:30:00 ちょうど以降なら Prep 以外**か を業務Bot が確かめる（丸めない・営業日の 0 時（ハワイ時間）から数える・日をまたいだ 0:30 は 24:30）。
- 名前ではなく Toast の Job の **ID** で判定する。区分（Prep／営業用／対象外）は GM・CEO が業務Bot の設定で選ぶ。区分の無い Job の打刻は「判定不能（Job 要確認）」。
- G1-P（Prep 専門職）は見ない（3 A）。G2 以上も見ない。だれが通常 G1 かは従業員マスターのグレード（肩書き・役職）と Prep の印で決め、判定したときの区分を案件に残す（6 A）。Toast の名前が従業員マスターで見つからない・同じ名前が 2 人以上は「判定不能」（8 A）。
- 指摘は勤怠の案件（朝 9:00 の「勤怠管理｜Moto・Yuki」の報告）に出る。同じ指摘は重ねて出さない。Toast で Job を直すと、次の確かめ直しで「解決」になる。
- **Bot は打刻・Job・時給を直さない。**

## 入れる前に

- SQL は要らない（設定は今の `bot_settings` の新しいキー `job_check`）。
- 本番の ops-bot が main（`a1348be`）のときのものと同じであること（戻す 1 ファイルは `a1348be` の ops-bot。Claude からは本番の中身が見えない）。確かめ方：Supabase → Edge Functions → ops-bot →「Deployments」（版の一覧）で、いちばん新しい版の日時が **2026-10-04 HST ごろ（PR #31 の配備）より後でない**こと。後の版があれば入れる前に Claude に知らせる（その版の中身が戻す 1 ファイルに入っていない）。

## 入れる順番

1. **Supabase → Edge Functions → ops-bot** を開き、中身を `1_関数_ops-bot_index.ts` に置き換えて Deploy。JWT の検証の設定は今のまま（変えない）。
   - これだけでは何も変わらない（設定 `job_check` が無いので、Job の指摘は出ない）。
2. アプリ v1105 をマージ（この PR）。GM・CEO の端末を更新する（版 1105）。
3. GM・CEO：経理センター → 業務Bot → メール認証 → 設定 → **「Job確認（16:30 基準）」**
   1. 店舗：LaLa（最初から LaLa が選ばれている）。開くと Toast の LaLa の Job を読み込む。
   2. Job ごとに区分を選ぶ：Prep の Job は **Prep**、ほかの営業の Job（Server・Kitchen など）は **営業用**、見なくてよい Job（Server Default など）は **対象外**。
   3. 「この店で使う」に印・基準の時刻 16:30・「この日の勤怠から」**2026-10-16**（最初から入っている）・G1-P は「見ない」（最初から）・補助の確認は使わない（最初から）。
   4. 保存。
4. 次の朝 08:40 からの自動の取得（当月の 1 日〜昨日）で、10/16 からの LaLa の勤怠を見る。すぐ見るなら、業務Bot →「Toastから取得」→ LaLa → 10/16〜昨日 →「Toastから勤怠を取得」。
5. 案件一覧の種類「Job確認（16:30）」で確かめる。1 件開くと、打刻の時刻・実際の Job → 期待・判定したときの区分が出る。

順番を入れ替えても壊れない：

- アプリを先に入れると、設定の「Job確認」を開いたときに読み込みで失敗する（何も変えない）。関数を入れてから開き直す。
- 関数を先に入れても、設定を保存するまで何も変わらない。

## 止めるとき・戻すとき

- 止める：設定で「この店で使う」の印を外して保存（新しい指摘は出なくなる。今ある案件はそのまま）。
- 関数を前に戻す：`戻す_関数_ops-bot_index.ts`（main のときの ops-bot）を貼って Deploy。設定 `job_check` は残る（使われない）。
  - 今ある Job確認の案件は**開いたまま**になる（前の関数は打刻の ID を `shifts` から読むが、Job確認の案件はそこに ID を置かないので、確かめ直しは「打刻の ID が無い」で止まり、閉じない）。新しい Job確認の案件は作られない。朝 9:00 の報告には開いている案件として出続けるので、不要なら業務Bot の画面で 1 件ずつ閉じる（または関数を v1105 に戻す）。

## 気をつけること

- 16:30:00 ちょうどは「以降」（営業用 Job でよい）。16:29:59 は「より前」（Prep であるべき）。
- Toast で Job の区間を分けて打刻した人は、区間ごとに見る（16:30 より前に Prep で始めて、16:30 から営業用 Job に打刻し直すのが正しい形）。
- 補助の確認（16:30 を過ぎても Prep のまま長く続く）は使わない（5 A）。使うときは設定で分を入れる（違反ではなく「確認」として出る）。
- 判定不能は違反ではない（Job が未分類・名前が見つからない・開始時刻が無い・G1-P の扱いが未設定）。設定か従業員マスターを直すと、次の取得・確かめ直しで正しく判定する。
- 名前は従業員マスター全体（ほかの店の人も）で探す。在籍の人を先に見る（同じ名前の退職した人がいても在籍の人で決まる）。
- 設定・従業員マスターを読めなかった日も、今の勤怠の確認（打刻漏れなど）は止まらない（Job確認だけが抜ける。取得の記録の「最後のエラー」に `job_check:` で残る。次の取得で読み直す）。
- 保存されている設定の形が壊れていると、その店の Job確認は止まる（設定の画面に赤字で出る。保存し直すと直る）。
- 「この店で使う」を外しても、今ある Job確認の案件は開いたまま（確かめ直しは「Job確認が止まっている」と記録するだけ）。要らなければ 1 件ずつ閉じる。
- 設定は店ごと・版つき。ほかの人が先に同じ店の設定を保存していたら、上書きせず読み直す（ほかの店の設定は消さない）。
- 時給・支給額は読まない・変えない（Toast の Job の一覧から時給は取り出さない）。
