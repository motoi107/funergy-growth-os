## 2. サーバー（SQL `20261126090000`・関数 work-requests）

- 列（`wr_requests`）：`pre_id`（uuid・事前経費の id）・`pre_by`・`pre_emp`・`pre_at`。索引 `wr_requests_pre_idx`・1 つの事前経費に実費は 1 つ（取り下げ・却下を除く）の一意の索引 `wr_requests_pre_one`（最後の守り）。
- `wr_pre_candidates`：RB を「経理の確認」できるときだけ（ほかは forbidden）。`wr_same_requester`（社員 ID が両方あればそれで・無ければ名前）・見られるもの・ほかの実費に結んでいないもの。
- `wr_link_pre`：client_key の押し直しは同じ答え（`replay`）・別の申請や別の操作に同じ鍵は conflict。2 つの行を id の順に押さえる。読んだ版（`expect_rev`）が違えば conflict。RB の「経理の確認」ができる人だけ（GM・本人・承認待ちのあいだは forbidden）。外す（pre が null）・同じものはそのまま（`same`）・事前承認済みでない／別の人／見られない は `pre_bad`・ほかの実費に結んである は `pre_taken`。超えたら RB を pending に（approved を消す）・履歴は `link_pre_over`（理由の文に予定・実費・差）・そうでなければ `link_pre`。事前経費の側の履歴に `actual_linked`（状態・版は変えない）。
- `wr_row`：段階 2 の形に足す（`jsonb_strip_nulls`）：`prev_amount_cents`（前の版の金額・`wr_versions`）・`link_pre`（番号・予定・状態・用途・結んだ人と時刻）・`link_over`・事前経費の `actual`（取り下げ・却下を除く）。
- `wr_stage` 7。新しい 4 つと置き換えた 2 つ（`wr_row`・`wr_stage`）は service_role だけ。段階 3 と v1164 の SQL が無ければ何も変えずに STOP。2 回流しても同じ。
- 関数 work-requests：`pre_candidates`・`link_pre`・エラー `pre_bad`・`pre_taken`（409）・`pre_missing`（503：SQL がまだ）。whoami の `fn: 8`。PIN の確かめ入りの非公開の 1 ファイルは Moto さんに直接（リポジトリに置かない）。
