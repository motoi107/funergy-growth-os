# ログイン・ページ・タブの読み込みの速さ（v1098）

依頼：Moto さん 2026-10-20 12:51 HST の添付「Funergy+ ログイン・ページ・タブ読み込みの高速化依頼」。
ログイン・各ページの表示・タブの切り替えに時間がかかる。実際のコードと通信を調べ、原因を特定し、直して確かめる。URL を分ける案も検討する。

このファイルは「何が遅かったか（数字つき）」「何を直したか」「何を変えていないか」「どう確かめたか」「残っていること」の記録。計測の数字は下の「計測」の節（同じ条件で直す前と直したあと）。

## 2. 原因（直す前・P1・GM・warm・5 回の中央値）

| 区間 | 直す前 | 主な原因 |
|---|---|---|
| ① 開いてからログイン画面が押せるまで | 1.27 秒（cold は 4.37 秒） | 名簿（従業員・店舗・PIN）を 1 つずつ取り終えるまで「スタッフ情報を読み込み中…」。cold は Service Worker が入ったときにページを 1 回読み込み直す（5 回中 3 回） |
| ② ログインを押してから PIN の確認まで | 0.10 秒 | （遅くない） |
| ③a 最初の画面が出て押せるまで | **18.2 秒** | ダッシュボードの描画 1 回が約 15 秒（下の A）。同期の画面（最大 9 秒）のあとに描く |
| ③b 裏の取り込みが終わるまで | **32.8 秒** | app_state 全部（約 22.7MB）を**圧縮なし**で取り（B）、解いて・合流して・書き直す。終わったらダッシュボードをもう一度描く（また約 15 秒） |
| ③c 通信が止まるまで | 44.0 秒 | 同上と、裏の Toast の補完・天気など |

ログインのあとの通信（warm）：87 件・24.1MB（そのうち app_state が 23.1MB）。

**A. Invoice を何百回も解き直していた（描画の時間の 9 割）**
ダッシュボード（GM）の描画 1 回で `ls('invoices')` が **546 回**呼ばれ、そのたびに全店分の Invoice（本番 約 4.5MB）を JSON から解き直していた（合計 13.8 秒／描画 15.0 秒）。呼んでいたのは日別の原価（`dayCostReal` → `_invDayCostMap`：作った表を覚えていたが、使えるかを確かめる前に毎回 `ls('invoices')` を呼んでいた）、原価（`monthInvoiceCostYm`）、ナビのバッジ（`navBadgeCount`：ページを開くたび）など。予実管理は 39 回（1.0 秒／1.2 秒）、人件費・勤怠は 172 回（4.3 秒／4.9 秒）、会議は 10 回（0.29 秒／0.54 秒）。
（測り方：描画のあいだ `ls` を包んでキーごとの回数と時間を数えた。CPU のプロファイルでも `_lsRaw`（JSON.parse）が 24 秒／35 秒）

**B. app_state を圧縮なしで全部取っていた**
`supaFetchAll` はページを Range ヘッダーで取っていた。ブラウザは Range ヘッダーの付いた要求に「Accept-Encoding: identity」を付ける（Fetch の決まり。Chromium で確かめた。Safari も同じ決まりだが実機では未確認）ので、サーバーは圧縮しない。ログインのたび（と「最新に更新」のたび）に約 22.7MB がそのまま届いていた。中には端末が取ってすぐ捨てる行（必要時だけ取る `ec_log` など約 1MB）と、前の統合行（`invoices`・`tasks_all` など約 7.4MB・分割へ移った古い行。毎回取り直して畳み込み直していた）がある。

**C. そのほか**
- ログインの同期（同期の画面）で、店ごとに売上 → 勤怠 → 前月のクレジットTip調整 → 出数を 1 つずつ待っていた（往復 4 回ぶん）。
- 初めて開いた端末で、Service Worker が入った（`clients.claim`）ときの合図で読み込み直していた（開いて 1〜3 秒後。PIN を打っている途中でも）。

**JavaScript の大きさ（7.4MB）**：2 回目からは Service Worker が HTML を端末から出すので通信はほとんど無い（ログイン画面までの通信 9 件・0.9MB は名簿など）。ログイン画面が出るまでのスクリプトの時間（CDP の ScriptDuration・目安）は P1 で約 0.27 秒、CPU 4 倍遅くで約 1.2 秒。ログインのあとの待ちに比べて小さい（5 を参照）。

**D. LaLa のページ**（計測の途中で見つけた・v804 から）：ページにいるあいだ、取り直し → 描き直し → Realtime の始め直し → 取り直し…が続いていた（3 の G4）。

## 3. 直したこと（v1098・アプリ index.html・sw.js と、読むだけの SQL 関数 1 つ）

計算式・権限・保存の決まり・画面の見た目は変えていない。変えたのは「同じものを何度も解かない」「圧縮して届ける」「変わっていない行を取りに行かない」「待たなくてよいものを待たない」だけ。

**A. 読むだけの Invoice の写し（`lsSplitRO`）**
- 端末に置いてある文字（統合キーと分割の行のすべて）が前と同じなら、前に解いた値を返す。1 文字でも違えば（保存・取り込み・ほかのタブ）今までどおり `ls()` で解き直す（前からある `_daRO` と同じ考え方）。
- 使うのは、数える・足す・新しい配列を作るだけの所（書き換えて保存する所は今までどおり `ls()`）：`_invDayCostMap`・`monthInvoiceCostYm`・`monthNonCostYm`・`monthInvoiceTotalYm`・`fcVendorMonth`・`_invPastPurpose`・`ipsManualList`・`navBadgeCount`・`pendingAcctReviewCount`・経理センターの一覧の行（`_acRows`）・画像の無い伝票の数。立替（`reimbursements`）は `plReimburseTotal` だけ。
- あわせて直した不具合：`_invDayCostMap` は作った日別の原価を「件数」で覚えていたので、件数が同じまま金額・日付を直した Invoice が日別の原価に出なかった（次に件数が変わるまで）。写しが同じもののときだけ使うようにした。

**B. まとめ取り（`supaFetchAll`）を圧縮されるように**
- ページを Range ヘッダーではなく `limit`・`offset` で取る（主キーの順：app_state・app_settings は key、マスターは SUPA_MASTER_MAP の pk）。並べる列が無い表（400）は、並べずに取り直す。
- 途中のページが読めなかったら「読めなかった」（null）。前は途中までの行を全件として返していた（マスターは丸ごと置き換えるので、残りの行が端末から消えていた）。
- 一度きりの「端末のデータをクラウドへ移す」（`migrateUploadLocalOps`）は、クラウドの一覧を読めなかったら何も送らない（前は「クラウドに 1 つも無い」とみなして端末の全部を送っていた）。

**C. app_state は変わった行だけ取る（`_kvPullRows`・`_kvSeenRecord`）**
1. 先に行の一覧（キーと中身の印）を取る。印は SQL の関数 `app_state_index`（`md5(value::text)`。中身が 1 文字でも変われば変わる。書いた人・端末の時計・updated_at によらない）。
2. 前に取り込んだときの記録（この端末だけの記録 `kv_seen_v1`・形は v:2。IndexedDB に置く。クラウドへ送らない・クラウドから受け取らない）と比べ、**クラウドの印が同じで、端末の写しも取り込んだときのまま**（写しの指紋＝長さ＋64 ビットのハッシュが同じ）の行だけ取らない。変わった行・端末に無い行・新しい行・端末の写しだけ変わった行（この端末で直して送った、ほかの経路で書き換わった）は取る（`key=in.(…)`）。前の統合行は畳み込んで端末に残らないので、印だけで比べる。
3. 名前で頼んだ行が答えに 1 つでも無ければ（キーの書き方の違い・あいだで消えた）、その回は全部取る（取れなかった行を「消えた」とみなさない）。
4. 取り込み方（合流・上書き・分割の畳み込み）は 1 行も変えていない（`_applyKvRows` に渡す）。取り込めた行だけ印と写しの指紋を記録する（端末に書けなかった行は次も取る）。一覧に無くなった行の記録は消す。IndexedDB をまだ読み終えていないあいだは記録しない（読み終えていない写しで記録しない）。
5. 全部取る（今までと同じ取り方）とき：初めての端末・記録が無いとき・前の形（v:1）の記録・7 日に 1 回・記録の時刻が端末の時計より先（時計を戻した端末）・設定の「クラウドから取り込む」・変わった行が多いとき（半分より多い）・一覧が読めない／0 行／形が違うとき。一覧が読めずに全部取ったあとは、次の回から変わった行だけに戻る。
6. SQL の関数がまだ無いとき：行の一覧を key・updated_at で取り、印は**前の統合行**（`invoices`・`tasks_all`・`skill_history` など、分割へ移った古い行。今は前の版の端末しか書かない）にだけ使う。ほかの行は今までどおり全部取る。
7. 取り込みで捨てる行（必要時だけ取る `ec_log`・`menu_log` など 6 つと人別の履歴 `spl_skill_history_*` など、端末だけのキー）は、前から端末に書かずに捨てていたので、取りに行かない（全部取るときもサーバーで外す）。読まれたときに取る仕組み（`_lsRequestDeferred`）はそのまま。
- 変わる動き（よい方）：前は、ログインのたびに「前の統合行」を畳み込み直し、人別の履歴（必要時だけ取る分割）が端末に無いと、その人の分割を作って 1 人ずつクラウドへ送っていた（読む・書く・確かめるの 3 回ずつ）。変わっていなければもうしない。
- 変わる動き（気をつけること）：前は、合流の決まりの無いキーは、ログインのたびにクラウドの値で端末を上書きしていた。いまはクラウドで変わっていなければ上書きしない（送れていない手元の変更は、未送信の送り直しで送る）。手元とクラウドがずれたままになる道を残さないように、7 日に 1 回は全部取り直す。

**D. ログイン画面をすぐ出す**
- 端末に名簿（従業員・店舗）があれば、IndexedDB を読み終えてから（3 秒まで）ログイン画面を出し、名簿は裏で取り直す。取り直したら、いま出している段（所属・名前）を描き直す。押している途中（0.7 秒以内に触った）なら少し待ってから描き直す（押した所が動かないように）。PIN を打っている段は何も描き直さない（打った PIN・「確認中…」・サーバーの知らせ・店舗PINの説明はそのまま）。「戻る」で名前・所属の段に戻ったときに新しい名簿で描く。
- 裏で取った名簿が遅れて届いたとき、取り始めたあとにほかが書いたキー（ログインのあとのまとめ取り・編集）は書かない（古い名簿で戻さない）。
- 名簿の無い端末（初めて開いた端末）は今までどおり取り終えてから出す。3 つの取得（従業員・店舗・PIN）は同時に。
- PIN はサーバーで確かめ、ログインのあとは取り直した名簿で役職・退職を確かめ直す（`resolveLoginIdentity`・`empBlocked`）ので、名簿が古いあいだに選んだ人でも、今までと同じ確かめを通る。

**E. ログインの同期で、店ごとの 4 つの取得を同時に**
売上（toast_sales）・勤怠（tip_labor）・前月のクレジットTip調整・出数（toast_item_sales）は別々の表を読んで別々のキーに書く（互いの結果を使わない）ので、同時に取る。同じ日を書く勤怠とクレジットTip調整の順は、v1090 の読み込みの番号（`_tipLaborSeq`）がこれまでどおり守る。前の 7 日の勤怠の補完（`backfillRecentLabor`）は、前と同じく売上・勤怠・クレジットTip調整が終わってから始める（勤怠を読み終える前に補完が同じ日を取りに行かないため）。

**E2. 設定の「クラウドから取り込む」は裏の取り込みまで待つ**
全部取るときは重い行（Invoice など）の取り込みを裏に回すので、「取り込みました」と出して読み込み直す前に、裏の取り込みが終わるまで（3 分まで）待つ。前の版は全部を待ってから出していた（同じ動き）。

**F. 初めて開いた端末で読み込み直さない**
Service Worker が初めて入ったとき（`clients.claim`）の 1 回の合図では読み込み直さない。そのあとの更新（ほかのタブで「更新」を押した）・前の版の Service Worker が動いていた（＝更新）・このタブで「更新」を押した、ではこれまでどおり読み込み直す。

**G2. ログインの同期の画面のあいだに、見えない画面を描かない**
差分の取り込みが同期の画面のあいだに終わるようになったので、取り込みの終わりの描き直し（v652 の `_heavyDone`）が、まだ出ていないアプリの枠にダッシュボードを描いていた（GM で約 1.3 秒。そのあと initApp がもう一度描く）。ダッシュボードを描くたびに「今日の売上」が店ごとに Toast に聞くので、ログインのあとの Toast の呼び出しが 14 回から 21 回に増えていた（直したあとの計測の途中で見つけた）。アプリの枠が出ていないときは描かない（initApp が取り込んだデータで描く）。直したあと 14 回（v1097 と同じ）。

**G3. 前の統合行は分割の行のあとに畳み込む**
まとめ取りを主キーの順にしたので、前の統合行 `invoices` が分割の行 `spl_invoices_…` より先に届くようになった。初めての端末では、分割の行がまだ無いうちに統合行を畳み込むので、統合行の記録を全部の分割の行に書き、送って、読み直していた（遅い回線の計測で app_state の読み直しが約 8.6MB・書き込みが 66 件。v1097 は 46 件）。取り込みの順を「分割の行が先・前の統合行があと」にした（`_applyKvRows`）。畳み込みは分割の行に無い記録だけを足すので、端末に残る中身は同じ。

**G4. LaLa のページで、取り直しと接続の作り直しが続いていた（v804 から）**
LaLa のページを描くたびに Realtime を始め直し、始め直すと取り直し、取り直すと描き直していた。ページにいるあいだずっと続き、10 秒で約 330 件の通信（取り直し約 160 回・接続約 170 本）と約 160 回の描き直しになっていた（v1097 で計測）。始め直すたびに新しい Supabase の接続を作るので、タイマーと受け口も 1 回の訪問ごとに増えていた（ページを 3 周すると、タイマー 7 → 16・受け口 28 → 64）。動いているときは始め直さないようにし、接続は通知・Tip Rate と同じ 1 つを使う（購読の名前は毎回変える。閉じている途中の同じ名前の購読を使わないため）。ログアウトと、ほかの道で LaLa から離れたあとの移動でも止め、LaLa を開くときは始め直してすぐ取り直す。直したあと 10 秒で 3 件、描き直し 2 回。

**G. 版**：`APP_VERSION`・`SW_BUILD` を 1098 に。更新の仕組み（新しい版は「更新」を押すまで切り替えない）は変えていない。

## 4. 計測（直す前 v1097・直したあと v1098・同じ条件）

## 5. URL を分けるか

**分けない（v1098 では入れない）。** 理由：

- 遅さの主な原因は、ページの JavaScript の大きさではなく、**同じデータを何度も解くこと（A）と、ログインのたびに約 22.7MB を圧縮なしで取ること（B・C）**だった。どちらも URL を分けても直らない（分けたページでも同じ `ls('invoices')` を呼び、同じ app_state を取る）。
- アプリの HTML は Service Worker が端末に置くので、2 回目からは HTML を取りに行かない（ログイン画面までの通信は 9 件・約 0.9MB で、名簿などのデータ）。JavaScript を解いて動かす時間は、ログイン画面が出るまでで P1 約 0.27 秒（v1098 で約 0.23 秒）・CPU 4 倍遅くで約 1.2 秒（同 約 0.9 秒）（CDP の ScriptDuration・目安）。ログインのあとの待ち（直す前 18〜74 秒）に比べて小さい。
- 分けると、ページを移るたびに共通の部分（ログイン・同期・合流の決まり・保存・権限の確かめ・Service Worker の更新の仕組み）をもう一度読み込んで解くことになる。いまは 1 回読み込めばページの切り替えは JavaScript だけで終わる（④ の数字）。共通の部分が全体の大半で、分けたぶん毎回の待ちが増えるおそれがある。
- このリポジトリには組み立ての仕組み（ビルド）が無く、`index.html` を GitHub Pages でそのまま出している。分けるにはビルドの仕組み・Service Worker の置くファイルの一覧・更新の仕組み（「更新」を押すまで切り替えない）をすべて作り直す必要があり、今回の「画面・保存・権限を変えない」の範囲を超える。
- 深いリンク（`#ページ名` で開く・通知から開く）・共通のログイン・ログインしていないときの戻し方は、いまのまま使える。

代わりにやること（次の段階の候補）：
1. 画面ごとの読み込み（URL は 1 つのまま、使う人の少ない重い画面のコードを、開いたときに別のファイルから読む）。どの画面を外に出すかは、ページを開いたときの数字（④）と使う人の数で決める。画面の見た目は変わらない。
2. 端末で速さを記録する画面（ログイン画面まで・ログインのあと・ページごと）。実機（iPhone）の数字を集められる。UI 案から。

## 7. 限界・確かめていないこと・残っていること

- **実機（iPhone の Safari・ホーム画面のアプリ）では測っていない。** 数字はこの VM の Chromium で、直す前と直したあとを同じ条件で比べたもの。
- 本番の Supabase の速さ（`app_state_index` の SQL の時間・行の一覧の時間）は測っていない。合成データで本物の PostgreSQL（PGlite）に流して、value が jsonb・json のどちらでも、答えの形・`md5(value::text)` と同じこと・中身を変えると印が変わること・接頭辞の行を返さないこと・確認の SQL が 6 行 OK・外す SQL で消えることだけ確かめた（`tests/app-state-index-sql.test.mjs`）。
- `app_state_index` は呼ぶたびに全部の行の md5 を計算する（786 行・22.7MB なら 1 ページ）。行が 1,000 を超えると 2 ページ目でもう一度計算する（関数は `set search_path` を付けているので、PostgreSQL がまとめて実行しない）。行がもっと増えたら、書くたびに印を表に残す見張り（trigger）に変える（表を変えるので、今回はしない）。
- 初めて開いた端末で、ちょうど開いているあいだに新しい版が公開されると、読み込み直さないぶん、次に開くまで前の版の画面のまま（「更新」の知らせは出る）。前は読み込み直していた。
- 4 回目の独立レビュー（`e55c7a5`・LaLa の見張りの直し）：P1・P2 なし。P3 のうち 4 つを直した（止めたあとに届いた答えでは描かない・始め直さない／go を通らずにほかのページを描いたときも止める／LaLa から LaLa を押したら始め直さずに 1 回取り直す／接続の名前は時刻ではなく数え札）。残したもの（v1091・前から）：通知（`rt-notifications`）と Tip Rate（`rt-tip-rate`）の Realtime は決まった名前の接続で、閉じている途中に同じ名前で作り直すと、閉じかけの接続を使うことがある（LaLa だけ別の名前にした）。
- 3 回目の独立レビュー（`49e8c54`・`e3d0a68`）の P3 で、直さずに残したもの（どれも v1097 から）：
