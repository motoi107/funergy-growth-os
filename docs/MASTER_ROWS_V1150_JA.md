## 1. 前（コードで確かめた・総点検の P1）

- 店舗（`m_stores` → 表 stores）・食材（`m_ingredients` → ingredients）・レシピ（`m_recipes` → recipes）・カテゴリー（`m_categories` → categories）は、保存のたびに**端末の全部の行**をクラウドの表へ書き直していた（`syncMasterToSupabase` → `supaUpsert`。upsert は行ごと上書き）。
  - 古い写しの端末が保存すると、ほかの端末が直した行・欄を前の値に戻した。
  - 消した行はクラウドに残り（upsert は行を消さない）、次のログインの取り込みで戻ってきた（「食材の削除が戻る」）。番号（コード）を付け替えた行も、前の番号の行が戻ってきた。
- 取り込み（`supaPullAllMasters`・`loginBootstrapPull`）は端末の表をクラウドの表で丸ごと置き換え、送れていない変更を消した。食材は裏で取り込む道があり、v1136 の「送れていない手元を残す」も通っていなかった。
- 従業員（v1085）・業者（v1121）は前から「変えた人・業者の変えた欄だけ」なので、この版では変えない。

## 2. いま

### 2-1. 変えたことを覚える（`mrOnEdit`・`lsSet` の中、書く前）

- 直す前と後の表を行の番号（クラウドの主キーと同じ決め方：店舗・レシピは id、食材・カテゴリーは code。レシピの id が無ければ code か名前）で比べ、変えた行の変えた欄・足した行・消した行を `_mr_touched_v1` に覚える（この端末だけ・送らない）。
  - 何回目の変更かの数（n）も覚え、送っているあいだにまた直した行は、送れたあとも覚えたまま（次に送る）。
  - 欄の順だけ違う・同じ中身の保存は覚えない。版の印（下の `_mrv`）は変えた欄にしない。
- 覚えは localStorage に書く。書けない（いっぱい）ときは IndexedDB の別の名前 `mr_touched_overflow` に持つ（送信待ちの `op_outbox_overflow` と同じ考え・5 の直し）。どれがいちばん新しいかは、書いた回 `_s` で決める（時計によらない）。
- 覚えを確かめられない保存は、そのキーに印 `_mr_unk_v1` を付け、送るときに**クラウドの表と行の版の印で確かめる**（2-2。5 の直しの前は全部の行を 1 回 upsert していた）。
  - 起動・取り込みの途中の保存（`_supaBooting`）、端末の保存（IndexedDB）を読み終える前の保存（店舗の表は localStorage にあるので除く）、前の値が無い保存、番号の無い行・同じ番号が 2 つある表。
  - v1149 以前に送れなかった変更（送信待ちにあり、覚えが無い）（`mrInitLegacy`）。
  - 覚えを localStorage にも IndexedDB にも書けなかった保存（5）。
  - 起動ごとに 1 回（IndexedDB を読み終えてから）、送信待ちにあるのに覚えも印も無い表（5）。
  - 印は、確かめ終えて端末の表がそのままのとき・送れていない変更の無い取り込みのときに外す。

### 2-2. 送るとき（`mrPush`・`syncMasterToSupabase` の中）

- 覚えている行だけ、クラウドから読む（40 行ずつ）。
  - 直した行：クラウドの行に、この端末で変えた欄だけを重ねる（この端末で欄を消していればクラウドからも消す）。
  - 足した行：丸ごと。
  - 消した行：**クラウドの行は消さず**、data に `_deleted:true`・`_deletedAt`（時刻）・`_deletedBy`（名前）を付けて書く。列は変えないので、サーバーの処理（Toast の取り込み・仕入れの集計など）が表を読む動きは変わらない（前も消した行はクラウドに残っていた）。
- **条件つきの書き込み**：data に版の印 `_mrv`（書くたびに新しい値）を置き、読んだときの版のままのときだけ書く（PostgREST の PATCH に `<主キー>=eq.<番号>` と `data->>_mrv=eq.<読んだ版>`、印の無い行は `is.null`。答えが空なら、ほかの端末が先に書いた）。新しい行は「まだ無い」ときだけ足す（POST・同じ番号があれば 409）。
  - 読んでから書くまでのあいだにほかの端末が同じ行を書いたら、こちらの書き込みは入らないので、読み直して重ね直す（4 回まで・少し待つ）。前は「書いたあと読み直して、自分の欄が入っていれば済み」だったので、あいだに書かれたほかの端末の欄を消していた（試験で再現）。
  - 6 本ずつ同時に書く。
- 一度に 100 行（`MR_BULK`）より多く書くとき（一度きりの移し替え・取り込みなど）は、行の数だけ通信しないように、まとめて書いて（500 行ずつ）読み直し、版の印がこちらの書いたままかを確かめる。あとからほかの端末が書いていた行は、読み直して重ね直す（少なければ条件つきの書き込み）。
- 書けた行の覚えを外し（送っているあいだにまた直した行は残す）、端末の行をクラウドに書いた行（ほかの端末の欄も入ったもの）にする。
- クラウドを読めない・書けないときは書かず、送信待ちに残す（理由は「設定 › 診断と記録」）。覚えも残る。
- **覚えを確かめられないとき（印 `_mr_unk_v1`）**：クラウドの表を全部読み、覚えていない行のうち中身が違う行を、行の版の印 `_mrv` で決める（5 の直し）。
  - 端末の行とクラウドの行の版の印が同じ（どちらにも無い、も同じ）＝端末が持っている版のあと、クラウドのその行をだれも書いていない → 端末の行を書く（条件つき）。
  - 違う（ほかの端末が先に書いた）・クラウドが消した印 → クラウドのほう。端末の行もクラウドの行にする（「設定 › 診断と記録」に 1 行。この端末で直していた場合、その変更は入らない）。
  - クラウドに無い行 → 足した行として入れる。
  - 端末に無くクラウドにある行 → この端末で消したのか、あとでほかの端末が足したのか見分けられないので送らない（限界）。
  - 覚えている行（欄）も、版の印が同じなら端末の行を丸ごと書く（覚えていない欄の変更も入る。だれも書いていないので、ほかの端末の欄は消えない）。違えば今までどおり覚えた欄だけ重ねる。
  - クラウドの表を読めなければ何も書かず、送信待ちと印を残す。表が空でも、消した行の覚えは送る。

### 2-3. 取り込むとき（`mrApplyPulled`）

- `supaPullAllMasters`（ログイン・「最新に更新」。食材は裏で取り込む道も）と `loginBootstrapPull`（店舗）で使う。
- クラウドの行のうち消した印の行は端末に置かない。まだ送っていない変えた欄・足した行はクラウドの行に重ね、この端末で消してまだ送っていない行は出さない。
- 送っている途中・覚えの無い送信待ちがあるときは、端末の表のまま（v1136 と同じ）。

### 2-4. ぶつかったとき

- ほかの端末が消した行を、この端末で直していた → **消したほう**（送らない・端末からも外す・「設定 › 診断と記録」に 1 行）。送るときも取り込むときも同じ。
- この端末で消した行を、ほかの端末が直していた → 消したほう（読み直して、消した印を付けて書く）。
- ほかの端末が消した行と同じ番号の行を、この端末で新しく作った → **作ったほう**（印を外して入れ直す・診断に 1 行）。
- 2 台がほぼ同時に同じ番号の行を新しく作った → あとで書いたほう（丸ごと・前と同じ）。
- 同じ行の別の欄を 2 台が直した → 両方残る。同じ欄を 2 台が直した → あとで書いたほう（前と同じ）。

### 2-5. 今までどおり

- 同期センターの「この端末からアップロード」（クラウドが壊れたとき用）は全部の行を書く。
- 従業員・業者は前からの仕組み。

## 6. 限界（5 のあと）

- 覚えを localStorage にも IndexedDB にも書けずに閉じたときは、端末に無くクラウドにある行（この端末で消した行）は分からないので送らず、次の取り込みで戻る（値の変更は版の印で確かめて送る）。
- 印のとき、端末の行とクラウドの行の版の印が違う行はクラウドのほう。この端末でも直していた場合（覚えを失っていた）、その変更は入らない（「設定 › 診断と記録」に 1 行）。
- v1149 以前の端末の書き込みは版の印を変えないので見分けられない（前からの限界）。
- 一度に 100 行より多い書き込みは条件をつけずにまとめて書き、あとから読み直して確かめる。読んでから書くまでのあいだのほかの端末の書き込みは見分けられない。「全部の端末が 1150 なら別の欄が消えない」は、この道を除く。
- サーバーの処理（invoice の紐づけ・仕入れの集計の区分）は消した印を見ないので、消した食材のコードも有効なコードとして扱う（前も消した行はクラウドに残っていたので、悪くはなっていない。サーバーでも外すかはあとで決める）。
- `mrOnEdit` は保存のたびに前後の表を読んで行ごとに比べる。食材 2,000 行の保存 1 回で約 12 ミリ秒（この環境の Node・合成データ。スマホではこの数倍かかりうる。実機は未計測）。
