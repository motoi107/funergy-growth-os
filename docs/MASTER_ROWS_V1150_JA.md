# v1150：店舗・食材・レシピ・カテゴリーのマスターは、変えた行の変えた欄だけを送る・消した行は戻らない（全体アップデート指示の 2c の 2 つ目）

- 依頼：Moto さん 11/12「次進めてください」。全体アップデート指示の順番（13A）の 2c の 2 つ目（マスターの表の書き方）。総点検の P1「食材の削除が戻る」を直す。「変わった」の合図は次の段（v1151・先に調べて、画面が変わるなら UI 案から）。
- アプリだけ（index.html・sw.js）。SQL・Edge Function・サーバーの設定の変更なし。表の列・主キー・権限は変えていない。行の data（jsonb）に印の欄を足す（下）。
- ブランチ `claude/master-rows-1150`（PR #143＝v1149 `eb275d2` の上）。

## 1. 前（コードで確かめた・総点検の P1）

- 店舗（`m_stores` → 表 stores）・食材（`m_ingredients` → ingredients）・レシピ（`m_recipes` → recipes）・カテゴリー（`m_categories` → categories）は、保存のたびに**端末の全部の行**をクラウドの表へ書き直していた（`syncMasterToSupabase` → `supaUpsert`。upsert は行ごと上書き）。
  - 古い写しの端末が保存すると、ほかの端末が直した行・欄を前の値に戻した。
  - 消した行はクラウドに残り（upsert は行を消さない）、次のログインの取り込みで戻ってきた（「食材の削除が戻る」）。番号（コード）を付け替えた行も、前の番号の行が戻ってきた。
- 取り込み（`supaPullAllMasters`・`loginBootstrapPull`）は端末の表をクラウドの表で丸ごと置き換え、送れていない変更を消した。食材は裏で取り込む道があり、v1136 の「送れていない手元を残す」も通っていなかった。
- 従業員（v1085）・業者（v1121）は前から「変えた人・業者の変えた欄だけ」なので、この版では変えない。

## 2. いま

### 2-1. 変えたことを覚える（`mrOnEdit`・`lsSet` の中、書く前）

- 直す前と後の表を行の番号（クラウドの主キーと同じ決め方：店舗・レシピは id、食材・カテゴリーは code。レシピの id が無ければ code か名前）で比べ、変えた行の変えた欄・足した行・消した行を `_mr_touched_v1` に覚える（この端末だけ・送らない）。
  - 何回目の変更かの数（n）も覚え、送っているあいだにまた直した行は、送れたあとも覚えたまま（次に送る）。
  - 欄の順だけ違う・同じ中身の保存は覚えない。版の印（下の `_mrv`）は変えた欄にしない。
- 覚えを確かめられない保存は、そのキーに印 `_mr_unk_v1` を付け、次は**今までどおり全部の行を 1 回**送る。
  - 起動・取り込みの途中の保存（`_supaBooting`）、端末の保存（IndexedDB）を読み終える前の保存（店舗の表は localStorage にあるので除く）、前の値が無い保存、番号の無い行・同じ番号が 2 つある表。
  - v1149 以前に送れなかった変更（送信待ちにあり、覚えが無い）も、最初の 1 回だけ全部の行で送る（`mrInitLegacy`）。
  - 印は、全部送れて端末の表がそのままのとき・送れていない変更の無い取り込みのときに外す。

### 2-2. 送るとき（`mrPush`・`syncMasterToSupabase` の中）

- 覚えている行だけ、クラウドから読む（40 行ずつ）。
  - 直した行：クラウドの行に、この端末で変えた欄だけを重ねる（この端末で欄を消していればクラウドからも消す）。
  - 足した行：丸ごと。
  - 消した行：**クラウドの行は消さず**、data に `_deleted:true`・`_deletedAt`（時刻）・`_deletedBy`（名前）を付けて書く。列は変えないので、サーバーの処理（Toast の取り込み・仕入れの集計など）が表を読む動きは変わらない（前も消した行はクラウドに残っていた）。
- **条件つきの書き込み**：data に版の印 `_mrv`（書くたびに新しい値）を置き、読んだときの版のままのときだけ書く（PostgREST の PATCH に `<主キー>=eq.<番号>` と `data->>_mrv=eq.<読んだ版>`、印の無い行は `is.null`。答えが空なら、ほかの端末が先に書いた）。新しい行は「まだ無い」ときだけ足す（POST・同じ番号があれば 409）。
  - 読んでから書くまでのあいだにほかの端末が同じ行を書いたら、こちらの書き込みは入らないので、読み直して重ね直す（4 回まで・少し待つ）。前は「書いたあと読み直して、自分の欄が入っていれば済み」だったので、あいだに書かれたほかの端末の欄を消していた（試験で再現）。
  - 6 本ずつ同時に書く。
- 一度に 100 行（`MR_BULK`）より多く書くとき（一度きりの移し替え・取り込みなど）は、行の数だけ通信しないように、まとめて書いて（500 行ずつ）読み直し、版の印がこちらの書いたままかを確かめる。あとからほかの端末が書いていた行は、読み直して重ね直す（少なければ条件つきの書き込み）。
- 書けた行の覚えを外し（送っているあいだにまた直した行は残す）、端末の行をクラウドに書いた行（ほかの端末の欄も入ったもの）にする。
- クラウドを読めない・書けないときは書かず、送信待ちに残す（理由は「設定 › 診断と記録」）。覚えも残る。

### 2-3. 取り込むとき（`mrApplyPulled`）

- `supaPullAllMasters`（ログイン・「最新に更新」。食材は裏で取り込む道も）と `loginBootstrapPull`（店舗）で使う。
- クラウドの行のうち消した印の行は端末に置かない。まだ送っていない変えた欄・足した行はクラウドの行に重ね、この端末で消してまだ送っていない行は出さない。
- 送っている途中・覚えの無い送信待ちがあるときは、端末の表のまま（v1136 と同じ）。

### 2-4. ぶつかったとき

- ほかの端末が消した行を、この端末で直していた → **消したほう**（送らない・端末からも外す・「設定 › 診断と記録」に 1 行）。送るときも取り込むときも同じ。
- この端末で消した行を、ほかの端末が直していた → 消したほう（読み直して、消した印を付けて書く）。
- ほかの端末が消した行と同じ番号の行を、この端末で新しく作った → **作ったほう**（印を外して入れ直す・診断に 1 行）。
- 2 台がほぼ同時に同じ番号の行を新しく作った → あとで書いたほう（丸ごと・前と同じ）。
- 同じ行の別の欄を 2 台が直した → 両方残る。同じ欄を 2 台が直した → あとで書いたほう（前と同じ）。

### 2-5. 今までどおり

- 同期センターの「この端末からアップロード」（クラウドが壊れたとき用）は全部の行を書く。
- 従業員・業者は前からの仕組み。

## 3. 試験（合成データ・本番に接続していない）

- `tests/master-rows-v1150.test.mjs`（23）：本物の `lsSet`・`_pushWithOutbox`・送信待ち・`syncMasterToSupabase`・`supaPullAllMasters`・`loginBootstrapPull` と v1150 の関数を VM で動かし、クラウドは PGlite（主キーと data jsonb の表）。条件つきの書き込み（PATCH の主キーと `data->>_mrv` の条件・POST の 409）も PGlite の SQL で同じ決まりにした。
  - 2 台が別の食材を直す → 両方残る・書くのは変えた行だけ（前は後の保存がもう片方を戻した）。
  - 2 台が同じ食材の別の欄を直す → 両方残る。
  - 消した食材が次のログインで戻らない・古い写しの端末が別の行を直しても戻らない・新しい端末にも来ない（前は戻った）。
  - ほかの端末が消した行をこの端末で直していた → 送るときも取り込むときも消したほう。消した番号で作り直す → 作ったほう。
  - ログインの取り込みが、送れていない変更（直した欄・足した行）を残し、ほかの端末の変更も見せる（前は食材の裏の取り込みが消した）。
  - 読んでから書くまでのあいだにほかの端末が同じ行の別の欄を書く（2 つの順番）→ こちらの書き込みは断られ、読み直して重ね直す・両方残る（条件つきにする前の v1150 では片方の欄が消えた）。
  - 2 台がほぼ同時に同じ番号を足す（足すのは断られ、読み直して版つきで書く）。消すのと直すのがほぼ同時（どちらの順でも）→ 消したほう（直すほうの書き込みは断られ、読み直して消した印を見る）。
  - 送る前に同じ行を 2 回直した（送れなかった）→ 両方の欄を送る。この端末で消してまだ送っていない行は、取り込みで戻らない・次の保存で消した印を送る。送っている途中の取り込みは端末の表のまま。
  - クラウドが書き込みを断る（500）→ 送信待ちに残り、次の保存で送る。
  - 一度に 150 行を直す → 1 回でまとめて書く・書いたあとほかの端末が書いた行は重ね直す。
  - 送っているあいだにまた直す・欄を消す・店舗・レシピ（空白のある id）・カテゴリー・`loginBootstrapPull`。
  - 起動の途中・端末の保存を読む前・v1149 の送信待ちは全部の行を 1 回（店舗の表は読む前でも覚える）。取り込みで印が外れる・送信待ちがあれば端末のまま。番号の無い行・同じ番号の行。
- 前の版（#143 の head `eb275d2`）の index.html を `FUNERGY_INDEX` で渡すと、場面の試験 5 件が落ちる（ほかは関数が無いので飛ばす）。
- わざと壊す 40 通り（保存・送る・取り込むところへのつなぎ・覚え方・条件つきの書き込み（版の条件・新しい版・断られたとき・足すのが断られたとき・やり直し）・消したほう／作ったほう・まとめて書く道・取り込みの重ね方・容量整理の守り）すべてで落ちる。1 回目に落ちなかった 4 つ（同じ行を 2 回直したときの欄・消した印の版・まだ送っていない削除の取り込み・送っている途中の取り込み）は試験を足して落ちることを確かめた。まとめて書く道を外す 1 つは、止める所まで来ずに試験が待ち続けたので、待つのに上限を付けて落ちるようにした。版の印を変えた欄にしない守り（`mrOnEdit` の `_mrv`）は、外しても送るときに版を新しくするので結果が同じ。
- 全体の試験・static release の結果は共有記録に。

## 4. 限界

- v1149 以前の端末は、今までどおり全部の行を書き直す（消した行を戻す・ほかの端末の欄を戻すことがある・前に取り込んだ版の印のまま書くので条件つきの書き込みとも比べられない）。**全部の端末を 1150 にすると効く**。
- 同期センターの「この端末からアップロード」も全部の行（端末の写しの版の印のまま）。
- 同じ行の同じ欄を 2 台が直したら、あとで書いたほう。
- 一度に 100 行より多い変更は、読んでから書くまでのあいだのほかの端末の書き込みを見分けられない（あとから書かれた分は重ね直す）。
- 起動・取り込みの途中の保存は前から送信待ちに入らないので、送る前に取り込みが来るとクラウドの値に置き換わる（前と同じ）。
- 消した行はクラウドに印付きで残る（行の数は減らない）。サーバーの処理が表を読むと、消した行も見える（前も同じ）。
