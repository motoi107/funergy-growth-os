- 「GM・CEO 以外の人がしている G1 からの昇格（従業員マスターの役職の変更・昇格申請の承認・Leader 昇格）はどうするか」→ **「GM・CEO だけにする」**（11/10・選択肢。ほかの人には理由を出して保存しない）。

v1143（PR #137）と同じ道（関数 `secure-state` の `swPut`・決めた人だけ・SQL の restrictive の決まり）に、グレード履歴を 1 つ足した。
**画面の決まりを 1 つ変えた（Moto さんの決定）**：グレードが変わる変更は GM・CEO だけ（前は G1 から上がる変更を AM・Head Chef・G4・経理・事務Crew・SL も保存・承認できた）。

## 1. なぜグレード履歴

`grade_hist` は社員ごとの「グレードが決まった日（確定日）・前後のグレード・前のグレードの期間に確定した評価（Career Score）・特例の理由」。
アプリが賞与の日割り（四半期の中のどの区間が何グレードか）と、前のグレードの期間の評価に使う。サーバーは読まない。
公開の鍵（anon）はアプリの中にあるので、アプリを開ける人ならだれでも書き換えられた（例：自分の確定日を前にずらして、上のグレードの日数を増やす）。

v1143 で外さなかった理由：新しく入った人の登録・昇格申請の承認・Leader 昇格でも書くため（だれが書いてよいかを決めてから）。11/10 に決まった。

## 2. 作り

- **関数 secure-state（v1145）**：`GH_KEYS = ['grade_hist']` を `SW_WRITE` に足した（**ceo・gm**）。v1143 の 8 つと同じ `swPut`：
  - だれか：今までと同じ（PIN のログインの印は work-requests の whoami、メールのログインは manager_auth）。役割はサーバーが決める。端末の言う役割は使わない。退職した人は 401。
  - GM・CEO でない人：**クラウドと同じ値**（欄の順は問わない）なら書かずに通す（`same:true`）。違う値は 403。
  - 値の形（GM・CEO が書くとき）：「社員 ID → 記録（オブジェクトか null）」の地図・キーは 200 字まで・600 万字まで。形の合わない記録は**クラウドにもうある同じ記録だけ**通す。外れれば 400。
  - `expect`（読んだ行の `updated_at`）があれば、そのときだけ書く（違えば 409）。
  - 読む（`get`）・取り込み（`pull`）には出さない（読むのは REST のまま）。答えにはいつも `ghfn:1`（と書いた人の役割 `by`）。
  - v1143 の 8 つ（`SW2_KEYS`）とは別の印にした。v1143・v1144 の関数は `sw2:1` を返すがグレード履歴を知らない（「知らないキー」と断る）ので、アプリがそれを見分けられるように。
- **アプリ v1145**：
  - 送る：`GH_KEYS`・`ghIsKey`。`swIsKey` は 11 のキー。`swRouted(key)` は、PIN かメールのログインがあり、関数が前の版と分かっていなければ、**書き込みだけ**を関数に頼む。関数が v1144 以前（答えに `ghfn:1` が無い）なら、10 分はグレード履歴を今までどおり REST で書く（`_ss.ghOld`）。
  - グレード履歴も **読んだ行が変わっていないときだけ書く**（`cas`。GM と CEO が同時に別の人の履歴を保存しても、両方残る。合流は今までどおり社員ごとに新しいほう `mergeMapByTime`）。
  - クラウドがもう端末の値をすべて持っていれば書かない（v1143 と同じ。GM・CEO でない端末の送り直しが止まらない）。
  - サーバーが断ったら（403・400）、そのことを出して送信待ちに残す。どの道で書いたかを「設定 › 診断と記録」に残す（「グレード履歴：サーバー（secure-state v1145）が書きました（役割 GM）」など）。手順の B-5 で使う。
  - **サーバーが断った送信待ちを外す（Moto さん 11/10「外すボタンを足す」・6 に詳しく）**：断られたキーに印を付け、右上の「保存」と「設定 › 診断と記録」に「断られたものを外す…」。確かめの画面のあと、この端末の値をクラウドの今の値に戻して送信待ちから外す。
  - **画面（Moto さんの決定）**：`ghChangeStopMsg(g0, g1)`。グレードが変わる（G1-P は G1 として）・ログインが GM・CEO でない、のとき「グレードが変わる変更（G1 → G2）は GM・CEO が行います」と出して、何も変えない・何も同期に送らない。
    - 従業員マスター（`ghBeforeSaveEmp`）：確定日の画面を出す前に止める（「役職・権限ロールを元に戻すと、ほかの変更は保存できます」）。端末に残っていた GM の確かめは、ほかの人の保存に使わない。
    - 昇格申請の承認・Leader 昇格（`ghGate`）：何も書く前に止める（「GM・CEO に承認してもらってください」）。却下は今までどおり。昇格申請の一覧には、GM・CEO 以外の人に「グレードが変わるので GM・CEO が承認します」。
    - グレードが変わらない役職の変更（例：Server Leader → Kitchen Leader）・昇格は、今までどおりだれでも（今までの権限の人が）できる。
    - 新しく入った人の登録（`ghAfterSaveEmp`）：GM・CEO 以外が登録したときは「入社の記録」を書かない。記録が無い人は入社日から今のグレード（`noHist`）で、入社の記録があるときと賞与の区間は同じ。成長カルテのグレード履歴では「確定日 未設定」になり、GM・CEO があとで足せる。
    - グレード履歴の画面での直し（`ghEdSave`）・取り込み（`ghImpRun`）は前から GM・CEO だけ（変えていない）。
- **SQL 20261114090000**：`ss_guard_key(k)` を 11 のキーに（v1141 の決まり `ss_guard_ins`・`ss_guard_upd`・`ss_guard_del` をそのまま使う）。v1141・v1143 の SQL がまだでも、この SQL だけで同じになる（RLS が OFF なら ON にして ss_open。印は v1141 と同じ）。2 回流しても同じ。
  読む（select）の決まりは足さない（行の一覧 `app_state_index` にも今までどおり出る）。
  - 戻すのは `db/secure-grade-hist-rollback.sql`（`ss_guard_key` を v1143 の 10 に戻すだけ。決まりが無ければ何もしない）。v1143 の戻す SQL を流すと v1141 の 2 つに戻る（グレード履歴も書けるようになる）。
- **確かめの SQL**：`db/secure-grade-hist-precheck.sql`（読むだけ・6 行：表・RLS・決まり・グレード履歴の人数と大きさと形・GM・CEO のアカウント）、`db/secure-grade-hist-postcheck.sql`（読むだけ・最後に rollback・19 行：v1143 の 17 行（キーは 11）＋グレード履歴の形・最後の保存の日時）。

## 5. 残る限界・次

- 読むのは今までどおり公開の鍵で読める（グレード履歴には社員 ID・名前・確定日・グレード・前のグレードの期間の評価の点が入る）。
- 従業員の表（役割・肩書き・店）は今も公開の鍵で書ける（(b) の段階）。サーバーの役割は manager_auth と work-requests の whoami で決めるので、グレード履歴の書き込みは従業員の表を書き換えても通らない。**ただし**、画面の「グレードが変わる変更は GM・CEO だけ」は端末の確かめで、従業員の表の役職そのものは今も公開の鍵で書き換えられる（グレード履歴に記録が残らないだけ）。
- GM・CEO 以外が登録した人には「入社の記録」が無い（計算は同じ。グレード履歴の画面では「確定日 未設定」）。
- ③ の前に公開の鍵で書き換えられていたかは分からない（④ の 19 行目でいちばん新しい保存の日時を見る）。

## 6. サーバーが断った送信待ちを外す（Moto さん 11/10「外すボタンを足す」）

- **なぜ**：決めた人だけが書ける設定（`swIsKey` の 11：グレード履歴・ガソリン代の単価・Score管理・賞与と Career Score の設定 8 つ）は、書く役割でない端末の変更をサーバーが断る（403。形の合わない記録は 400）。断られた変更は何度送っても届かず、送信待ちに残り続け、右上に「送信待ち」が出たままになっていた（消す画面が無かった）。
- **印**：`ssPutRow` が 403・400 を受けたら、そのキーにこの端末だけの印 `_ss_refused_v1`（キー → 断った時刻と 403／400。中身は持たない）を付ける。サーバーが受け付けたとき（同じ値で通したときも）・送信待ちから外れたときに消す。一覧（`ssRefusedList`）は「今ログインしている人の送信待ち」と「印」の両方があるものだけ。`swIsKey` でないキー（成長カルテ・賞与の行・Career Score など）には付けない（範囲で決まる写しなので、クラウドの値で置き換えると見られない人の分まで変わりうる）。
- **画面**：
  - 右上の「保存」：送れていないものの下に「このうちサーバーが断ったもの N 件（このままでは届きません）：グレード履歴」と、ボタン「断られたものを外す…」（確かめの画面を開くだけ）。Head Chef など「診断と記録」を開けない役職もここから外せる。
  - 「設定 › 診断と記録」：送れていない保存の 1 件ごとに「サーバーが断りました（変えられる人が決まっている設定です）」と「外す…」、ボタンの列に「断られたものを外す…」。「送れていない保存の一覧」の画面にも 1 行とボタン。
  - 診断の数：「サーバーが断った保存 N 件」を、「何度送っても送れない保存」とは別に数える（同じものを 2 回数えない）。
  - 断ったときの知らせ（ガソリン代・Score管理・賞与と Career Score の設定・グレード履歴）に「要らない変更なら、右上の「保存」の「断られたものを外す」で外せます」を足した。
- **確かめの画面**（`openRefusedDrop`）：外すものの名前・断った時刻・理由（変えられる人が決まっている設定／形の合わない記録）、「外すと、この端末の値をクラウドの今の値に戻し、送信待ちから外します。この端末で入れたこの変更は消えます（元に戻せません）。変更が要るなら、GM・CEO に伝えて入れ直してもらってください」。GM・CEO のログインのときは「外す前に、メールのアカウントと社員の ID の結びを確かめてください（結びを直せば外さずに送れます）」。押すまで何も変えない。
- **外す**（`ssDropRefused`・`ssDropRefusedRun`）：確かめの画面に出したキーだけを、1 つずつ：
  1. 今の人の、断られた送信待ちでなければ外さない（ほかの人の送信待ちは、その人がこの端末でログインしたときに出る）。送っている途中なら外さない。
  2. クラウドの今の行を読む（REST・15 秒で打ち切る）。読めなければ外さない（「クラウドを読めませんでした（つながる所でもう一度）」）。
  3. 読んでいるあいだに、この端末でまた保存された・送り始めた・送信待ちから外れた・ログインが変わった、のときは外さない（「確かめのあいだにこの端末でまた保存されました」）。
  4. この端末の値をクラウドの値で**置き換える**（合流しない＝断られた記録は端末から消える）。クラウドに行が無ければ端末の値を消す。端末に書けなければ外さない。
  5. 送信待ちから外し、印を消す。クラウドには何も書かない。「設定 › 診断と記録」の記録に「サーバーが断った送信待ちを外しました：グレード履歴（この端末の値をクラウドの値に戻した）」（中身は残さない）。今の画面を描き直す。
- **変わらないこと**：だれが書けるか（サーバーの決まり）・送る道・合流・ほかの送信待ち（断られていないもの・成長カルテ・Career Score の断り）は今までどおり。外した変更の控えは残さない（端末の容量を使わないため。要る変更は GM・CEO が入れ直す）。
- **前からのこと（変えていない）**：共有の端末で、GM・CEO 以外の人の断られた変更が端末に残っているあいだに GM・CEO が同じ設定を保存すると、端末の値（その変更も含む）が GM・CEO の権限で送られる。
