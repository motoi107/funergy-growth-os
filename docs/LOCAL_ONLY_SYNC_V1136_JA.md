# v1136：端末にしか残っていなかった手入力をクラウドへ・取り込みが送れていない変更を消さない

- 依頼：Moto さん 11/03「Funergy+ 全体アップデート指示」（保存・同期の総点検と統一）。段階 1 の報告（Docs「Funergy+ 保存・同期の総点検とワークセンター再設計（段階 1 の報告）」）の決めてほしいこと 1〜13 に「全部A」（12 は「保存・同期・診断の状態はどのページにいても表示」に変えて A）。
- この版は進める順番の 2a（端末にしか残らない業務データ）。12 の表示・「保存しました」の直し・同期と診断のボタンの整理は v1137。
- アプリだけ（index.html・sw.js）。SQL・Edge Function の変更なし。

## 1. 前の状態

次の 4 つは、どの同期の一覧（`OP_SYNC_KEYS`・`OP_SYNC_PREFIX`）にも入っておらず、入れた端末にしか残っていなかった（コードで確かめた）。

| データ | 前のキー | 起きていたこと |
|---|---|---|
| 勤怠の手動修正 | `att_override_<店>_<日>` | 直した端末だけ Labor・Tip が直る。ほかの端末の Labor・Tip・エラーの一覧は Toast の値のまま |
| Tip の期間の確定 | `tip_confirm_<店>_<初日>` | ほかの端末では「確定済み」に見えない。v1129 の「前の期間の確定を確かめる」（`tipBackPull`）はクラウドを読んでも何も無かった（ほかの端末で確定した期間に遡れた） |
| 手入力 KPI | `kpi_manual_<期間>` | リピート率・口コミ・Totoya のカウントが端末ごとに違う |
| 育成の記録 | `dev_data`・`dev_start` | 育成パイプライン（志望・ステージ・テスト・再教育・開始日）が端末ごと |

どれも端末をなくすと消える。

あわせて、合流の決まりの無いキー（議事録の振り返り・評価・応募者・食材の新マスターなど）は、取り込み（ログイン・「最新に更新」・1 つ取る）でクラウドの値に丸ごと置き換わった。送信待ち（op_outbox）に入っていた手元の変更は、置き換わったあとの送り直しがクラウドの値を送るので、黙って消えていた。

## 2. 変えたもの

### 2-1. 新しい名前（クラウドへ送る）

| データ | 新しいキー | 中身 | 合流 |
|---|---|---|---|
| 勤怠の手動修正 | `att_fix_<店>_<年-月>` | `{ '日': { data, by, at, _at } }` | 1 件ずつ新しいほう。取り消しは `{ _deleted:true, by, at, _at }` |
| Tip の期間の確定 | `tip_cf_<店>_<年>` | `{ '初日': { status:'確定済み', …, _at } }` | 1 件ずつ新しいほう。解除は取り消しの印 |
| 手入力 KPI | `kpi_man_<期間>` | `{ '店': { repeatRate, …, _ft:{欄:時刻}, _at } }` | 店ごと・欄ごとに新しいほう（消した欄は消したまま） |
| 育成の記録 | `dev_pipe` | `{ '名前': { stage, tests, …, _ft, _at } }` | 名前ごと・欄ごとに新しいほう |
| 育成開始日 | `dev_pipe_start` | `{ '名前': { d:'日', _ft, _at } }` | 同上 |

- 合流の決まりはどれも `strict`（クラウドを読めなかったら書かない＝端末の写しで丸ごと書かない）・`keepLocal`（書き戻すとき手元のあとからの変更を残す）。
- 勤怠と Tip は月・年ごとの入れ物にした（日ごと・期間ごとの行にすると app_state の行が増え続けるため）。
- 欄ごとの時刻：古い写しの端末がステージを進めても、ほかの端末で足したテストの記録は消えない。リピート率と Totoya のカウントを別の端末で入れても両方残る。保存の時刻は「前の記録のどの時刻よりもあと」（時計の遅れた端末でも、見てから直した欄が勝つ）。何も変えずに保存しても時刻は進めない。
- 時刻が同じで中身が違うとき（前の版の記録どうし）は、どちらの順に合流しても同じ答え。配列・入れ物は和集合、値（ステージ・OJT の状態など）は記録を丸ごと比べて決めた側から採る（ステージと OJT の状態が別々の記録から来て食い違わない）。中身の比べ方はキーの順によらない（`_cjson`。クラウドの jsonb はキーの順を変える）。
- 無かった欄に空の配列・空の入れ物（画面が初めから渡す形）を入れても「直した」にしない。育成の記録の無い人は、画面の初期値（空のテスト・スキル・カリキュラム・再教育）と比べる（独立レビューの P1：ほかの端末で入れたテスト・スキルを、この端末の空の初期値が消していた）。
- 画面が受け取る値に `_ft`・`_at` は入れない（getKpiManual・getDevData）。
- 容量の整理（`LS_NEVER_FREE`）で新しい名前も前の名前も消さない。送信待ちの名前（outboxLabel）を足した。

### 2-2. 新しい名前にした理由

前の版（v1135 まで）の端末は app_state の行を全部受け取り、合流の決まりを知らないので丸ごと置き換える。同じ名前のままクラウドへ送ると、まだ更新していない端末で、その端末にしか無い入力がクラウドの値で消える。新しい名前なら前の版の端末は読まない（その端末の前の名前の記録はそのまま残り、更新したときに移し替える）。

### 2-3. 前の名前の記録の移し替え（`v1136MoveLocalOnly`）

- ログインのあと（PIN のログインと管理者ページの両方・3 秒後）、この端末の前の名前の記録を新しい名前に足して送る。毎回動くが、同じなら何も書かない。
- 前の記録の時刻は「前の版の帯」（分の数。今の保存の時刻＝ミリ秒よりずっと小さい）。ほかの端末がもう新しい名前で保存した記録・取り消しには勝たない。前の版の記録どうしは時刻（`at`）の順。KPI・育成の前の記録は時刻 0（新しい名前で直した欄がいつも勝ち、新しい名前に無い欄だけ埋まる）。
- 新しい名前で直した欄と前の記録の同じ欄が出会ったとき（2 回目の独立レビュー P2-2）：入れ物（スキルの Lv・カリキュラム）は項目ごとに足す（新しいほうが勝ち、前の記録にしか無い項目を足す）。配列（テスト・再教育・ステージの履歴）は前の記録にしか無い要素を前に足す（画面は配列の最後を「いちばん新しい結果」と読むので、前の版の古いテストが最新に見えないように）（中身が同じか、真偽の欄（済み など）だけが違う要素は同じとみなす＝済みにした再教育を前の写しで二重にしない）。値（ステージ・目標・OJT の状態など）は今までどおり新しいほう。前は新しいほうで丸ごと置き換え、まだ更新していない端末にしか無かったスキル・テストが、ほかの端末で同じ欄を直したあと消えた。
- 前の版で取り消した勤怠の修正・解除した確定（空の値）は移さない。
- 起動・取り込みの途中、同期が OFF のときはしない（送れないまま「済み」にしない）。端末に保存できなかったら済みの印を付けず、次のログインでもう一度。
- 前の名前の記録は消さない（戻すときのため）。読むときは新しい名前を先に見て、移し替えが済むまでは前の名前も見る（済んだら見ない）。

### 2-4. 取り込みが送れていない変更を消さない（`_pullKeepLocal`）

合流の決まりの無いキーは、取り込みでも「新しく書いたほう」を残す（キー全体で新しいほう）。

| 場合 | 取り込みで |
|---|---|
| 送っている途中（`_pushBusy`） | 手元を残す（送り終えれば、クラウドはこの値になる） |
| この人の送信待ちがあり、手元を直した時刻がクラウドの行の更新時刻（app_state の `updated_at`）よりあと | 手元を残す（あとで送る） |
| クラウドの行のほうが新しい（ほかの人があとで書いた） | クラウドの値（ほかの人の新しい変更を古い写しで消さない） |
| 時刻が分からない（v1135 までの送信待ち・行の時刻が無い） | クラウドの値（今までどおり） |
| ほかの人の送信待ち（共有の端末） | クラウドの値（今までどおり） |

- 手元を直した時刻：合流の決まりの無い app_state のキーを、端末の保存の中身が本当に変わったときだけ覚える（`_pend_edit_at`・`lsSet`）。同じ中身の保存・送信待ちの送り直し・まとめて送る・起動中・同期 OFF では進めない（2 回目の独立レビュー P2-1：前は送るたびに覚えたので、送り直しのたびに「今直した」になり、ほかの人のあとの変更を古い写しで消しえた）。送れたら忘れる（`_outboxRemove`）。
- クラウドの行の時刻はマイクロ秒まで読む（`_tsMicro`・PostgREST の 6 桁）。直した時刻はミリ秒なので、比べた結果は今の Chrome・Safari の `Date.parse` と同じ（6 桁を読めない環境のための守り）。
- 中身が同じで欄の順だけ違う保存も「直した」にしない（`_cjson` で比べる）。
- 読み取りに `updated_at` を足した：`_kvFetchKeys`・`_kvPullRows` の全部取り・`pullOpKey`。
- 設定（app_settings）とマスターは更新時刻を読まないので、送っている途中のときだけ手元を残す（`supaPullAllMasters` の設定とマスター・`pullSettingKey`）。
- 合流の決まりのあるキーは今までどおり合流する（`pullSettingKey` は合流の決まりがあれば合流するようにした。使っているのは tip_policy だけで、合流の決まりは無い）。
- まだ取得していない必要時のキー（履歴など）は今までどおり取り込む（手元は部分の値なので）。
- 残した行は「取り込めた行」に数えない（v1098 の差分の取り込みで次も取る）。
- 独立レビューの P2 で直したこと：最初の形（送信待ちがあればいつも手元）は、ずっと送れない変更があるとそのキーがその端末で止まり、読み込み直したあとの古い写しがほかの人の新しい変更を消した。時刻で比べる形にした。

### 2-5. ほか

- `tipBackPull`：クラウドの年ごとの入れ物を読み、その初日の記録が「確定済み」で取り消しの印でなければ止める。
- Tip の前の期間の確かめの文：「この端末で確定した記録はありません」→「その期間を確定した記録は見つかりませんでした」（確定はクラウドで共有になった。前の版の端末の確定は見えないので「無い」とは言わない）。
- `getAttOverride` は記録の写しを返す（読んだ入れ物を呼び出し側が書き換えられない）。
- 移し替えは、端末の保存（IndexedDB）を読み終えるまでしない（一部しか見えないまま「済み」にしない）。
- 版 1136（APP_VERSION・SW_BUILD）。

## 3. 入れたあと変わること

- ほかの端末でも、手動修正の入った日の Labor・Tip・勤怠のエラーの一覧が、修正した端末と同じになる（今まで違っていた）。Tip の画面の額は確定済みの期間でも計算し直して出す（前から）。修正した端末で確定した期間は、ほかの端末の額も確定の額と同じになる。
- 修正していない端末で確定していた期間は、ほかの端末の修正が届くと画面の額が確定の記録（`rows`・`totalFinal`）と違って見えることがある。確定の記録そのものは変えない（気づけるようにするかは次の版で決める）。
- ほかの端末でも「確定済み」が見え、前の期間への Tip Rate の遡りが止まる。
- 手入力 KPI・育成パイプラインがどの端末でも同じ。

## 4. 変えていないもの

計算式・権限・承認・Toast の取り込み・確定の記録の中身・前の名前の記録（消さない）・合流の決まりのあるキーの取り込み・送信待ちの仕組み。

## 5b. Codex のレビュー（#130 6627627177・#131 6627869364）の P2 2 件の直し（11/04・Claude）

## 6. 限界・確かめていないこと

- 実機（iPhone）・本番のデータ・本物の Supabase では確かめていない。
- 前の版（v1135）の端末で入れた手入力は、その端末を 1136 にしてログインするまでクラウドに届かない（その端末にはそのまま残る）。全員の端末を 1136 に。
- 前の版の端末どうしで同じ日・同じ店の記録が違っていたら、移し替えでは時刻の新しいほうが残る（勤怠・Tip）。KPI・育成は欄ごとに、時刻の無い記録どうしは決まった順（配列は和集合）。
- 取り込みの守りは「この人の送信待ち」で、手元のほうが新しいときだけ。クラウドのほうが新しければ手元の送れていない変更は今までどおり消える（キー全体で新しいほう。本当に直すには、そのキーに合流の決まりを付ける＝段階 2c）。共有の端末でほかの人の送れていない変更も今までどおり。比べる 2 つの時刻はどちらも端末の時計（直した時刻はこの端末、`updated_at` は最後にその行を書いた端末のアプリが書く）。時計が進んだ端末は、ほかの人のあとの変更より自分の送れていない変更を新しいとみなし、送ったときに上書きしうる（時計が遅れた端末は、自分の変更を捨てる側＝今までどおり）。
- 送信待ちの送り直し（flushOutbox）が端末の値を丸ごと送り、ほかの人の新しい変更を消すことがあるのは前から（段階 2c）。
- 前の版の記録（分の数の時刻）は、新しい名前で保存した記録にいつも負ける（前の版の端末で、あとから直していても）。前の版の記録どうしの順は、記録の時刻の文字（端末の時間帯）で比べるので、日本とハワイの端末では最大 19 時間ずれる。
- 移し替えはログインのたびに前の名前のキーを読み直す（同じなら書かない）。そのたびに前の版の中身が足されるので、育成の記録に「消す」「要素の値を直す」作りを足すときは、移し替えを 1 回だけにするなどの変更が要る（コードの `_fsFill` に書いた）。IndexedDB を使えない端末（`_idbState` が unavailable）は、記録が全部 localStorage にあるので移し替える。
- ロールアウトのあいだ、まだ更新していない端末にしか無い値（ステージ・目標・OJT の状態など、入れ物・配列でない欄）は、更新した端末で同じ欄を直すと、そちらが勝つ（「Leader志望に登録」が自動で入れるステージも、直した欄になる）。全員の端末を 1136 にしてから育成の記録を直すのが安全。
- 前の版の記録を足したあと、その記録を受け取っていない端末が同じ欄を直すと、新しいほうで置き換わり、足した前の版の中身はまた消える（新しい版の 2 台が同時に同じ欄を直したときと同じ「新しいほう」）。前の版の記録のある端末が次にログインすると、移し替えでまた足される（その端末がもうログインしなければ戻らない）。前の版の記録が 2 つ以上と時刻のある記録が出会うときの足し方（配列の並び・同じ項目の値）は合流の順で違うことがあるが、同じ時刻の欄どうしは次の合流で和集合にそろう（`_fsTie`）。
- 前の版の記録どうし（どちらも時刻なし）の配列の和集合（`_fsTie`）は、真偽の欄だけ違う要素を別の要素として残す（前から。2 台の前の版の端末がどちらも同じ再教育を持ち、片方だけ済みにしていると、済みでない写しも残る）。前の版の記録どうしの値の決め方（`_fsRecWin`）も 3 つ以上では順によることがある（同じく次の合流でそろう）。
- 直した時刻（`_pend_edit_at`）は localStorage に書く。書けない（容量がいっぱい）・2 つのタブで同時に直すと覚え損ねることがあり、そのときはクラウドの値を採る（今までどおりの側）。
- グレードを変えるまとめた保存（`ghTxn`）が途中で戻ったときは、直した時刻も戻す。
- 食材マスター（m_ingredients）の裏の取り込み（ログインのあと）は今までどおり手元を上書きする。
- 新しい行（Tip の確定の額・勤怠の時間・育成のテストの点）は、ほかの業務データと同じく公開の鍵で読める app_state にある（段階 2b で直す）。
- 公開の鍵で app_state を読み書きできるのは前から（段階 2b で直す）。
- 項目ごとの時刻（`_fi`）・配列の和集合（要素の `_t` の順）は、2 つ・3 つの記録の合流の順によらない（試験と独立レビューで確かめた）。要素の `_t` は画面の記録にも入る（画面は使わない）。
- cas の道はクラウドの `updated_at` を読んで比べる（v1096・v1097 と同じ）。SQL で 5 つのキーを直すときは `updated_at` も変える（Handbook と同じ決まり）。
