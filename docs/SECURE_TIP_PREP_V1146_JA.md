依頼：Moto さん 11/03 の「Funergy+ 全体アップデート指示」の 2b（機密・権限に関わるデータを公開の鍵から外す）と、11/10 の回答。
- 次の作業 →「**Tip Rate とプレップから**」（11/10・選択肢）。
- だれが変えてよいか →「**今の画面で決められる人だけ**」（Tip Rate の承認・却下・引き上げ、プレップの認定・時給の表をサーバーで）。

v1141〜v1145 と同じ道（関数 `secure-state` が書く・SQL の restrictive の決まりで公開の鍵の書き込みを止める）に、3 つのキーと人ごとの Tip Rate の行を足した。
**だれが何を変えられるかは変えていない**（今の画面で決められる人と同じ）。画面の決まりは 1 か所だけそろえた（下の 2 の「プレップの認定の承認」）。

## 1. なぜ Tip Rate とプレップ

- `spl_tip_requests_<名前>`（人ごとの Tip Rate の申請・決定）と前の統合行 `tip_requests`：v1092 からチップの配分の重み（その日の Tip Rate）に使う。
- `prep_tables`（プレップの Lv と時給の表）・`prep_certs`（プレップの認定）：v1106 から時給（その日の Lv × 表）と人件費に使う。
- どれも app_state の行で、公開の鍵（アプリの中にある）で書けた。アプリを開ける人ならだれでも、自分の Tip Rate を「承認」にする・時給の表を書き換える・自分の認定を足す、ができた（お金に直結）。
- 読むのは今までどおり公開の鍵で（どの端末もチップの配分と人件費を計算するため）。

## 3. 作り

- **関数 secure-state（v1146）**：`put` が `tpIsKey`（`prep_tables`・`prep_certs`・`tip_requests`・`spl_tip_requests_` で始まる名前）を `tpPut` へ。
  - だれか：今までと同じ（PIN のログインの印は work-requests の whoami、メールのログインは manager_auth）。端末の言う役割は使わない。退職した人は 401。
  - `expect`（読んだ行の `updated_at`）があれば先に照らす（違えば 409）。そのあと読んだ行で確かめ（`tpCheck`）、**その行が変わっていないときだけ書く**（違えば 409）。
  - Tip Rate を決められる人か（`tipDecider`）：役割 ceo・gm・am ならいつも。staff なら、確かめた G4 以上で、今の社員の表の役割が g4（ワークセンターの前だけ）か chef（Corporate Chef はいつも・Head Chef はワークセンターの前だけ。どちらも `confChef`＝今の社員の表と確かめた写しの両方で Head Chef）。社員の表を読めなければ決めない側に倒す。
  - 本人か：行の名前（`spl_tip_requests_` のあと）と、この人の名前（PIN の印・確かめた写しの名前と、社員の表の自分の行の列と data の名前＝`tipActorNames`）のどれかが、書き方をそろえて（`tipNk`：NFKC・空白を 1 つに・前後の空白を取る・小文字）同じか。名前が 1 つも分からないログイン（社員と結ばれていないメールのアカウント）は、申請を足せず、決めることもできない。社員の表を読めないときは失敗（500。端末は送信待ちに残して送り直す）。
  - 形：Tip Rate は配列・2000 件まで・各記録に id（80 字まで・重ならない）・名前は行の名前と同じ・状態は 申請中／承認／却下・率は 0〜100。プレップは「ID → 記録」の地図。どちらも 400 万字まで。形の合わない記録は**クラウドにもうある同じ記録だけ**通す（400）。名前の長い行（200 字を超える）は書かない（400）。
  - 決める人でなくても、**クラウドと同じ値**なら書かずに通す（`same:true`・v1141 と同じ）。
  - 答えにはいつも `tpfn:1`（と書いた人の役割 `by`）。読む（`get`）・取り込み（`pull`）には出さない（読むのは REST のまま）。
- **アプリ v1146**：
  - 送る：`TP_KEYS`・`tpIsKey`・`gwIsKey`（v1141〜v1145 の 11 と合わせた「決めた人だけが書ける」キー）。`swRouted` は、PIN かメールのログインがあり、関数が前の版と分かっていなければ、**書き込みだけ**を関数に頼む。関数が v1145 以前（答えに `tpfn:1` が無い）なら、10 分は Tip Rate・プレップを今までどおり REST で書く（`_ss.tpOld`）。
  - `tip_requests`（と人ごとの行）・`prep_certs` も **読んだ行が変わっていないときだけ書く**（`cas`。2 台で同じ人の Tip Rate・認定を同時に保存しても、両方の変更が残る。合流は今までどおり：Tip Rate は `mergeTipReq`＝決めた時刻の新しいほう、認定は記録ごとに新しいほう）。`prep_tables` は v1106 から `cas`。
  - サーバーが断ったら（403・400）、理由を出して送信待ちに残す（「この Tip Rate の記録は、このログインでは変えられません…」「プレップの時給の表を変えられるのは GM・CEO です…」など・日英）。v1145 の「断られたものを外す」も Tip Rate・プレップに効く。
  - どの道で書いたかを「設定 › 診断と記録」に残す（「Tip Rate（〈名前〉）：サーバー（secure-state v1146）が書きました（役割 GM）」など）。手順の B-5 で使う。
  - 送信待ちの名前（`outboxLabel`）：「プレップの時給の表」「プレップの認定」「Tip Rate（名前）」。
- **SQL 20261115090000**：`ss_guard_key(k)` を 11 のキー＋`tip_requests`・`prep_tables`・`prep_certs`・`spl_tip_requests_` で始まる名前（長さによらず）に（v1141 の決まり `ss_guard_ins`・`ss_guard_upd`・`ss_guard_del` をそのまま使う）。v1141〜v1145 の SQL がまだでも、この SQL だけで同じになる。2 回流しても同じ。読む（select）の決まりは足さない。
  - 戻すのは `db/secure-tip-prep-rollback.sql`（`ss_guard_key` を v1145 の 11 に戻すだけ）。
  - `prep_cfg`（店の設定）・`spl_tip_history_`・`live_tip_rate`（ほかの端末への合図）は含めない（公開の鍵で今までどおり書ける）。
- **確かめの SQL**：`db/secure-tip-prep-precheck.sql`（読むだけ・11 行：表・RLS・前の決まり・Tip Rate の人ごとの行の形・前の統合行にだけある記録・プレップの表と認定の形・Tip Rate を決められなくなる人の数・ワークセンター・社員と結ばれていない GM・CEO・GM・CEO のアカウント）、`db/secure-tip-prep-postcheck.sql`（読むだけ・最後に rollback・22 行：v1145 の 19 行（キーは 15）＋Tip Rate の行の形・プレップの形・いちばん新しい決定と保存の日時）。名前は出さない。

## 6. 残る限界・次

- 読むのは今までどおり公開の鍵で読める（Tip Rate の率・状態・決めた人、プレップの Lv・時給の表・認定）。
- 確かめていない AM・G4・Head Chef・Corporate Chef は、今の画面でボタンを押してもサーバーが断る（v1131 からの決まり。① の 8 行目で数を見る・GM・CEO が確かめる）。
- 社員の表（役割・名前）は今も公開の鍵で書ける（(b) の段階）。サーバーは役割を確かめた写しと合わせて決めるので、書き換えだけでは決める人にならない。ただし本人かどうかは名前で決める（同じ名前の人がいると区別できない＝v1140 と同じ）。メールのログインの GM・CEO が社員の表の自分の行の名前（列と data の両方）を書き換えると、自分の Tip Rate の行を「ほかの人」と見なせてしまう（PIN のログインなら確かめた写し・印の名前も見る。書き換えは `employee_field_log` に残る）。
- 前の統合行 `tip_requests` にだけある前の決定（時刻なし）を、決める人でない端末が人ごとの行へ移そうとすると断られる（値は変わらない・① の 5 行目。GM・CEO の端末で「最新を取得」すると移る）。
- 社員と結ばれていないメールのアカウントは、自分の Tip Rate を申請できない・Tip Rate を決められない（名前が分からない）。① の 10 行目は GM・CEO だけを数える。
- `prep_cfg`（評価項目の名前と説明）は対象にしていない（店長も直せる。お金に直接はかからない）。
- ③ の前に公開の鍵で書き換えられていたかは分からない（④ の 22 行目でいちばん新しい決定・保存の日時を見る）。
- v1145 の戻す SQL を v1146 のあとに流すと、Tip Rate・プレップもまた公開の鍵で書けるようになる（この一式の戻す SQL を使う）。
