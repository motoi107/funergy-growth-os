## 1. 依頼と決定

- 2b の残りを調べた結果：「本人の画面も使う賞与の設定」は v1148 で済んでいた。公開の鍵で読める個人の情報が残っていたのは **通知（app_state の `notifications`）** だけ。

## 2. 前

- 通知は app_state の 1 行（新しい 500 件の配列）。公開の鍵（anon）でだれでも読めて、だれでも書けた。
- 中身の例：退職手続きの開始（名前・理由・最終出勤）、オンボーディング（採用した人の名前）、お悩み相談の題名、特別育成の指名（個人あて）、承認の知らせ。
- どの端末もログインのたびに全部を取り込み、画面（`notifForMe`）で自分あての分だけを出していた。店のタブレットにも全部が入っていた。

## 3. いま

### 関数 secure-state（`supabase/functions/secure-state/handler.mjs`）

- 頼み `nt`：`{ add:[通知…（20 件まで）], read:[id…], ack:[id…] }`。何も無ければ読むだけ。答えに `ntfn:1`。
- **読む**：ログインした人の宛先の分と、自分が出した分（`ntVisible`）。決まりは画面の `notifForMe` と同じ（試験でランダムの 4,000 件を比べる）：
  - 個人あて（`toUser`）：その人だけ。
  - 店あて（`toStore`）：その店の人。役割（`toRoles`）があれば、その役割の人だけ。CEO・GM・経理・事務Crew は全店。
  - 役割だけ：その役割の人。
  - だれあてでもない通知：出した人だけ（前から）。
- **役割と店**（画面の curRole・curStore・応援・担当の店に当たるもの。`ntCtx`）：
  - CEO・GM・経理・事務Crew（whoami の役割）＝全店。確かめた AM（whoami の am）＝担当の店と自分の店。
  - スタッフ：社員の表の役割（公開の鍵で書ける）は、**GM・CEO が確かめた写し（wr_people）のグレードが足りるときだけ**使う
    （G2＝2・SL＝3・G4＝4・Head Chef＝4 と Head Chef の印）。そのときの店は確かめた写しと今の社員の表の重なり（v1147 の `protStores` と同じ）。
    確かめがまだの人・G1 は crew（自分の店。今の社員の表）。Store Manager の肩書きの SL は `sm` あても。
- **足す**：形を確かめて整える（`ntClean`：id は英数字と `_:.-` の 100 字まで・欄の名前・長さ・入れ物は 1,000 字まで・既読と確認の印はサーバーが空に・`_` で始まる欄は捨てる・
  5 分より先の時刻と 400 日より古い時刻は今に）。同じ id は足さない。システムの知らせ（出した人が「システム」）は同じ refId を二度足さない
  （端末は自分に見えない分を確かめられないため）。出した人は関数が確かめた人（システムの知らせはシステムのまま）。
- **印**：既読（`readBy`）・確認（`ackBy`。既読も）に自分の名前を足すだけ。見られない通知には付けない。ほかの人の印・中身は変えない・消さない。
- 新しい順に 500 件を残す（アプリの `mergeNotifs` と同じ）。読んだ行が変わっていないときだけ書く（変わっていたら読み直して重ね直す・5 回まで）。変わらなければ書かない。
- **ログインを確かめられない端末**（店舗の PIN のタブレット・PIN が初期の人・メールのログインが切れた人）：**足すだけ**（読む・印は 401）。
  出した人は書いてあるまま・確かめていない印 `_u:1`。変更の記録（v1151）は「サーバー」。この関数の 1 つの実行環境の中で 10 分に 300 件まで（429）。
- 答え：`{ done:[受け取った id], bad:形が合わず足さなかった数, level:'fn'|'add', items:[見られる通知]（ログインした人だけ） }`。

### アプリ v1152（`index.html`）

- `ntMode()`：`fn`＝関数で読み書き（PIN でログインした人）／`add`＝関数で足すだけ（店のタブレット・ログインの印の無い人）／
  `rest`＝今までどおり（関数が無い・前の版・PIN の確かめ先が答えない（10 分）・印の無い GM・CEO）。
- 端末の写しの印：`_s`＝クラウドにある（関数から受け取った）／`_sr`・`_sa`＝クラウドに自分の既読・確認の印がある／`_w`＝足した人（送るまで）。
  `_s` の無い通知は「まだ送っていない足した通知」。
- **送る**（`ntPush`・`syncMasterToSupabase` の app_state の道の先頭。送信待ち・送り直しも同じ道）：足した通知（このログインの人が足した分・20 件ずつ）と、
  クラウドにまだ無い自分の既読・確認の印だけ。送れなければ送信待ちに残す。ほかの人が足して送れなかった分は、その人のログインで送る（14 日で捨てる）。
- **読む**（`ntPull`）：ログイン（`notifRealtimeStart`）・画面に戻ったとき・1 分ごと・「変わった」の合図（v1151。`notifications`・`_secure:notifications`）・`pullOpKey`。
  合図で読むときは、合図より前に頼んだ読み（途中のもの）を待ってから読む。読めなかったら（false）間をおいてもう一度（v1151 の直し・`docs/CHANGE_SIGNAL_V1151_JA.md` の 9-1）。
  答えで端末の写しを置き換える（まだ送っていない足した通知・自分の印は残す）。頼んでいるあいだに送った答えで新しい写しを置いたら、古い答えは置かない（`_nt.rx`）。
- REST の取り込み（`_kvPullRows`）では通知を取らない。app_state の Realtime も購読しない（公開の鍵では読めない行になるため）。
- **v1152 の形にする**（`ntMigrate`・端末に 1 回。`_nt_mig_v1152`）：REST で取り込んだ通知は「クラウドにある」とみなす。送信待ちが残っていたときだけ、
  3 日のうちに自分（またはシステム）が足した通知を送り直す（関数は同じ id を足さない）。店のタブレットではほかの人の通知を端末から消す。
  REST の道に戻ったら印を外し、関数の道に戻ったときにもう一度直す（REST で取った分を「足した」として送り直さない）。
  印を外すのは `ntMode` が「今までどおり」と答えたとき（関数が前の版・PIN の確かめ先が答えない 10 分・印の無い GM・CEO）と、
  関数が前の版と分かったとき（`ntPull`・`ntPush`）と、REST で全部を取り込んだとき（`onNotifIncoming`）。
  外さないと、500 件を超えて押し出された通知が自分の名前で戻る（わざと壊す試験で見つけて直した）。
- **ログアウト**（`ntOnLogout`）：クラウドから受け取った通知は端末に残さない（次の人に出さない）。まだ送っていない足した通知だけ残す。
- 通知の画面・ベル：店のタブレットには「店舗の PIN のタブレットでは通知を出しません。自分の PIN でログインすると見られます。」、
  ログインの印の無い人には「通知を見るには、自分の PIN を設定してログインし直してください。」（日英）。
- 版：APP_VERSION・SW_BUILD 1152。

## 4. 変わること（Moto さんに伝える）

- 通知の中身は公開の鍵で読めなくなる（③ のあと）。端末にも自分あての分だけ。
- 店のタブレットには通知を出さない（Moto さんの決定）。タブレットで作った通知は今までどおり届く。
- **Claude が決めたこと**：
  - PIN が初期のままの人（ログインの印が無い・GM・CEO 以外）には通知を出さない（足すだけ）。ほかの機密のキー（v1139〜v1148）と同じ。自分の PIN にすると見える。
  - GM・CEO の確かめがまだの店長・リーダー・G4・Head Chef・AM は、確かめるまで crew あての通知だけ（v1147 の店の範囲と同じ考え。① の 7・8 行目）。
  - ログインを確かめられない端末からも足せる（今までどおりだれでも足せる。読めない）。出した人の名前は確かめていない印付き。
  - システムの知らせは同じ refId を二度足さない。

## 5. 限界

- 足すのは今までどおりだれでもできる（公開の鍵を知っていれば関数で足せる。10 分に 300 件まで）。たくさん足されると古い通知が押し出される（前からの 500 件の上限）。
- 社員の表の役割・店（公開の鍵で書ける）は、確かめた写しがあるときだけ使うが、crew あての通知の店は今の社員の表（応援の店を書き足せば、その店の crew あての通知は見える）。
- 既読の印にはほかの人の名前も入っている（前から。確認の画面がだれが確認したかを出すため）。
- 店のタブレットで作った通知の「出した人」は確かめていない（タブレットの印は関数で確かめられない＝work-requests が社員 ID の無い印を断るため）。
- 1151 以前の端末は ③ のあと通知を読めず送れない（全部の端末を 1152 にしてから ③）。
- 実機（iPhone・店のタブレット）・本番のデータでは確かめていない。

## 8. Codex #146（`c98dd95` の 6845284151・`5ed341f` の 6846844817）の指摘の直し（11/13・Claude・関数とアプリ。SQL は変えていない）

### 8-1. #145 から取り込んだ 3 件（`docs/CHANGE_SIGNAL_V1151_JA.md` の 10）

- まとめての同期に渡したキーは、預かったあとに始まった同期が「最新」で終わるまで取り直す／保護の区分は 50 より多いキーと一緒でも 1 つずつ／個人の欄が変わったら描き直す。
- v1152 で足したこと：関数で通知を読む端末では、通知の行（`notifications`）の合図も 1 つずつ（REST の取り込みは通知の行を読まないので、まとめての同期では取れない）。
  関数が前の版の端末（REST の道）は今までどおり。`_secure:notifications` は v1152 のはじめから 1 つずつ。

### 8-2. P2：確かめた G2・G4 に役割あての通知が届かなかった

- 前：関数は確かめた役割を社員の表の名前（`g2`・`g4`）のまま宛先（`toRoles`）と比べた。アプリはログインで g2 を `sl`、g4 を `am` として扱い（`ROLE_ALIAS`）、
  宛先も `sl`・`am` で出すので、画面では見えるはずの通知が関数から返らなかった。
- 今：関数も同じ名前にそろえる（`NT_ROLE_ALIAS`）。G2 で Store Manager の肩書きの人は `sm` あても（画面の `isStoreManager` と同じ）。確かめがまだの人は今までどおり crew あてだけ。
- 限界：画面は、店舗マスターの AM 欄にその人の名前がある店も「担当の店」とする（`_amManagesStore`）。関数は G4 の店を、確かめた写しと今の社員の表の重なりだけにする（狭いほう）。

### 8-3. P2：通信が切れているあいだの「確認しました」・既読がログアウトで消えた

- 前：ログアウトで受け取った通知（`_s`）を端末から消すとき、まだ送れていない自分の印も一緒に消えた。
- 今：ログアウトのとき、まだ送れていない自分の既読・確認の印だけを、**だれの印か（社員 `p:<社員 ID>` と名前）と通知の id** で端末に残す（`_nt_marks_v1152`・中身・題名は残さない・14 日・500 件まで）。
  同じ人がもう一度ログインして関数から通知を受け取ったら、その通知に印を戻して送る（送れたら消す。また送れずにログアウトしたら、また残す）。
  ほかの人のログインでは使わない・送らない。店のタブレット・社員と結ばれていないログインでは残さない。

### 8-4. 名前だけで決める個人あての通知（Claude のレビュー・Codex が同意）

- 前：個人あて（`toUser`）と出した人（`by`）は名前だけで比べたので、同じ名前の別の人（別の店）にも同じ個人あての通知を返した。
- 今：関数は、その名前を持つのが本人だけのときだけ、名前あての通知と自分が出した通知を返す（社員の表の名前・GM・CEO が確かめた写しの名前・退職した人も。前後の空白はそろえて比べる。v1140 の Career Score と同じ考え）。
  同じ名前の人がいれば、どちらにも返さない（店・役割あての通知は今までどおり）。社員の表が読めないときは、通知を読むこと全体を失敗にする（端末は前の写しのまま。名前あての通知を黙って消さない）。
- 限界：宛先を社員 ID にはしていない（通知を出すところが多い）。同じ名前の 2 人は、名前あての通知を見られない（直すには社員の表の名前を分ける）。

### 8-5. P3：形の合わない通知が黙って消えた

- 大きすぎる入れ物（1,000 字を超える欄）は、その欄だけ外して届ける（前は通知ごと関数に断られ、端末からも消えた）。
- それでも関数が受け取らない通知（id・欄の名前の形）は、端末に残さず（送り直しても同じ）、知らせと「診断と記録」に「通知 N 件は形が合わず送れませんでした」と出す。
- 残したこと（Moto さんの判断）：ログインを確かめられない端末が「システム」の名前・同じ refId で足せる（前から。だれでも足せる仕組みのまま）。
