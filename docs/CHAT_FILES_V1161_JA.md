## 2. サーバー

- SQL `supabase/migrations/20261124090000_chat_files.sql`（先にチャットの SQL `20261121090000`。無ければ何も変えずに STOP。2 回流しても同じ）。
  - Storage に「置き場所を限らない」決まり・chat-files を開ける決まりがあれば、何も変えずに STOP（公開の鍵で添付を読めてしまうため）。
  - 置き場所 `chat-files`（非公開・1 つ 10MB まで・決まった形だけ）。中の名前は意味のない番号（`<会話の id>/<ファイルの id>`、小さい写真は `.t` を付ける）。
  - 表 `chat_files`（だれの・どの会話の・どのメッセージの・状態 up／ok／bad／sent／del／purging／gone・申請に付けたか）。RLS ON・公開の鍵では読めない・書けない。
  - 関数（どれも security invoker・サーバーの鍵だけ）：`chat_file_start`（上げる準備・同じ鍵は同じ 1 つ）・`chat_file_pending`・`chat_file_mark`（確かめた結果）・`chat_files_access`（開ける人か）・`chat_files_list`（7A）・`chat_file_purge_list`／`chat_file_purged`（消す分）・`wr_receipt_from_chat`（8B）・`wr_receipt_file`。
  - 置き換え：`chat_send`（ファイルは 5 つまで・本人の・この会話の・確かめたものだけ・本文は空でもよい）・`chat_edit`（ファイルのあるメッセージは本文を空にできる）・`chat_delete`（5A）・`chat_msg`（ファイルを付ける・消した／見えなくしたものは出さない）・`chat_row`（本文が空なら「写真 2 枚」など・申請の版と本人か）・`chat_limits`・`chat_stage`（2＝添付）。
- 関数 work-requests（handler.mjs）：
  - `chat_file_start`：種類・大きさをサーバーで決め、1 回だけ使える上げる先（Storage の署名つき URL）を返す。
  - `chat_send`（ファイルあり）：上げたものの先頭 16 バイトと大きさを確かめてから送る（写真は小さい写真も）。まだ無ければ `file_missing`（アプリが上げ直す）・合わなければ `file_bad`。
  - `chat_file_url`：5 分だけのリンク（1 つ・小さい写真は 30 までまとめて・保存は名前つき）。`chat_files`：一覧。`wr_receipt_chat`／`wr_receipt_url`：8B。
  - あと片づけ（消したメッセージのファイル・1 日たった送らないファイル・消しかけのまま 10 分）は答えを返したあとに裏で（EdgeRuntime.waitUntil）。置き場所から消せなかったら 10 分後にもう一度。
  - whoami は `fn: 7`・`chat: 2`。添付の SQL がまだなら `files_missing`（503）。前の版の関数なら `unknown_action`（アプリは「v1161 になってから」）。
- 本番に貼る関数は非公開の 1 ファイル `work-requests_v1161_index.ts`（handler.mjs ＋ PIN の確かめ＋起動の行・Moto さんに直接）。v1159 の中身に添付を足したもの（申請の段階 2・3 とチャットは今までどおり）。

## 3. アプリ（v1161）

- 入力欄の左の 📎 で付ける（複数可）。付けたものは入力欄の上に並ぶ（× で外す）。写真は縮めているあいだ「縮めています…」で、終わるまで送らない。
- 送る：ファイルごとに 上げる準備 → 置き場所へ PUT（この Supabase の Storage の上げる先だけ）→ メッセージを送る。送れなかったら「もう一度送る」（同じ鍵：サーバーではメッセージもファイルも 1 つ）。上げた答えが届かず 2 回目に「もうある」と言われたら、そのまま次へ。置き場所に無い（`file_missing`）と言われたら 1 回だけ上げ直す。「消す」で文とファイルが入力欄に戻る（中身が名前と合わなかったものは戻さない）。
- 見る：写真は小さい写真を並べる（1 枚なら縦横の比で大きく）。押すとこの画面の中で大きく見る（保存・申請に付ける）。ほかのファイルは名前・大きさ・「開く」「保存」。開くときは押したときに新しい窓を開いておき、リンクが届いたらそこへ（あとから開くと端末が止めるため）。開けない端末では押して開くリンクを出す。https のリンクしか使わない。
- 小さい写真のリンクは 30 ずつまとめて頼み、4 分は使い回す。送った写真はこのタブで作った小さい絵をそのまま使う（読みに行かない）。
- 一覧の 1 行：本文が空なら「写真 2 枚」「ファイル「〇〇」」など。
- 直す：ファイルのあるメッセージは本文を空にできる。消す：「付けたファイル（N つ）もサーバーから消えます（申請の領収書にしたものは申請に残ります）」と聞く。
- 申請に付ける（8B）：建て替え経費の申請のチャットで、申請した本人に、写真・PDF のところへ出す（承認待ち・差し戻しのあいだ・まだ付けていないもの）。古い画面（版が違う）は断られて読み直す。答えが届かず押し直しても同じ鍵（版は 1 つだけ進む）。付けたものには「申請に付けた」。申請の画面の領収書は「開く（チャットの写真：名前）」で、その申請を見られる人が開ける（サーバーが確かめる）。まとめて承認の「開いた」の印にも数える。
- **この端末には残さない**：付けたファイルの中身・小さい絵は送るまでこのタブのメモリだけ。ログアウトで捨てる（小さい絵の URL も放す）。共通データ・localStorage・IndexedDB には書かない。

## 5. 限界

- 実機（iPhone・Android・PC のブラウザ）では確かめていない。写真の縮小（createImageBitmap・canvas）・新しい窓・保存（content-disposition）は試験では代わり。iPhone のホーム画面のアプリでの保存の動きは未確認。
- HEIC の写真は、端末が読めれば JPEG にする（読めなければ「この写真を読めませんでした」）。
- 中身の確かめは先頭 16 バイトと大きさだけ（Office のファイルの中身・ウイルスは見ない）。
- 本番の Storage の答えの形（署名つき URL・Duplicate・Range）は Supabase の文書どおりに作った（本番では未確認）。
- 前の版の関数（v1159 以前）に戻すと、送ったファイルも開けなくなる（消えてはいない）。

## 6. #155 の Codex（6876878458）の直し（アプリ v1161 のまま・同じ SQL の置き換え）
