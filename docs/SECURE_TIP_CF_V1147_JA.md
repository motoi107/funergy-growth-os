## 1. なぜこの 2 つ

- `tip_cf_<店>_<年>`（Tip の期間の確定。v1136 からクラウドへ）：期間ごとに、人ごとの最終チップ額・時間・率が入る（`{ 初日: 記録 }`。解除は `{ _deleted:true }`）。
- `warnings_<店>`（注意ログ。必須チェックで記録）：日付・記録した人・理由（必須タスク未完了の数と名前）。足すだけの記録。
- どちらも app_state の行で、公開の鍵（アプリの中にある）で**全店の分を読めて書けた**。アプリを開ける人ならだれでも、ほかの店の人のチップ額を読む・確定を解除する・注意ログを消す、ができた。

## 3. 作り

- **関数 secure-state（v1147）**：
  - キー：`scIsKey`（`tip_cf_`・`warnings_` で始まり、その後ろに 1 文字以上・200 字まで）。`scParse` で種類と店（`tip_cf_<店>_<年>`。形の合わないキーは店なし＝全店を見られる人にだけ見え、だれも書かない）。
  - 範囲：`scScope(a)`（上の表）。`scOut` が `{ level: all|scoped|none, stores, tip, wn, confirm, unlock, wnWrite }`。
  - 取り込み（`pull`）：アプリが `sc_have`（この端末にある行の印）を送ったときだけ、答えに `sc`（範囲・行の一覧と印・変わった行だけ）を付ける。範囲を決められない（社員の表が読めない）ときは `{ error:'scope' }`（端末の写しはそのまま）。
  - 1 つの行：`get` は見られる行だけ（403）。`put` は `scPut`：見られない行は 403 → クラウドと同じ値なら書かずに通す → `expect` で 409 → 形と権限（`tcfCheck`・`wnCheck`）→ **読んだ行が変わっていないときだけ書く**（409）。
  - `tcfCheck`：記録を消さない・変えた記録は正しい形（キーが年の中の YYYY-MM-DD・`status:'確定済み'` で `from` がその日・`rows` は 2000 件までの配列、か `_deleted:true`）・解除（`_deleted`）と例外承認（`forced`）と、**今効いている確定（解除されていない記録）を書き換えること**は解除できる人・ほかは確定できる人（まだ確定していない日・解除された日を確定する）。
  - `wnCheck`：足すだけ。前の記録は `_mut` と、id の無い前の記録に中身から作った id（アプリの `_wnKey` と同じ）を付けることだけ（記録の鍵ごとに、`_mut`・`id` を除いた中身の組が前と同じであること。前からある鍵で新しい中身を足す＝ほかの記録の id を借りる、もできない）。新しい記録は記録できる人・欄は `date`・`by`・`reason`・`id`・`_mut` だけ。
  - `tcf_status`（前の期間の確かめ・アプリの `tipBackPull`）：店（30 まで）と初日を受け、確定している店の ID だけを返す（額は返さない）。Tip Rate を決められる人（`tipDecider`）は店によらず、ほかは見られる店だけ。
  - 答えにはいつも `scfn:1`。
- **アプリ v1147**：
  - 取り込み：`ssPull` が `sc_have` を送り、`scTake` が答えを受ける（見られない店の行とクラウドに無くなった行を端末から消す・送れていない変更のある行は残す・範囲を `_sc_state` に記録）。REST の取り込みは 2 つの種類を取らない（`not.like`）。関数が前の版（`scfn` が無い）なら、今までどおり REST（範囲の記録も消す）。
  - 頼んだあとにログインが変わったら、届いた答えを使わない（v1140 と同じ：`ssStale`・`ssStaleRows`）。前の人の範囲が残っているあいだは見せない・書かない。
  - 書く：`ssRouted` が 2 つの種類を関数へ（読むのも書くのも）。`warnings_` も**読んだ行が変わっていないときだけ書く**（`cas`。`tip_cf_` は v1136 から）。`lsSet` の入口 `scLocalWriteOk`：見られない店の行・記録できない人の注意ログは、この端末で作らない（知らせる）。
  - 断られたとき（403・400）：理由を出して送信待ちに残す（日英）。v1145 の「断られたものを外す」も効く（見られない店の分は、クラウドを読まずにこの端末の写しを消すだけ）。どの道で書いたかを「設定 › 診断と記録」に残す（「Tip の期間の確定（S1）：サーバー（secure-state v1147）が書きました（役割 …）」）。
  - 画面：チップ管理の確定の欄は、見られない店なら「このログインでは見られません」（未確定に見せない・確定のボタンも出さない）。解除・例外承認のボタンは解除できる人だけ。必須チェックは見られない店なら警告の数を「—」・履歴の代わりに知らせ、記録のボタンは記録できる人だけ。本人の成長画面の注意ログは、見られない店があれば「注意ログなし・良好」と言わない。注意の中身はエスケープ（前はしていなかった）。
  - 前の期間の確かめ（`tipBackPull`）は `tcf_status` で。関数が前の版なら REST で行を読む（今までどおり）。
  - 前の名前の記録の移し替え（v1136）は、見られない店の分を移さない。
  - 送信待ちの名前：「注意ログ」を足した。
- **SQL 20261116090000**：`ss_secret_key` に `tip_cf_`・`warnings_` で始まるキー（長さによらず）を足し、`ss_secret` を作り直す（v1139〜v1144 の SQL がまだでも、この SQL だけで同じ。RLS が OFF なら ON にして `ss_open` を足す。ほかの決まりがあれば止める）。2 回流しても同じ。
  - 戻すのは `db/secure-tip-cf-rollback.sql`（`ss_secret_key` を v1144 の形に戻すだけ。RLS は ON のまま）。
- **確かめの SQL**：`db/secure-tip-cf-precheck.sql`（読むだけ・10 行：表・前の決まり・RLS・確定の行と記録の形・注意ログの形・店の表に無い店・確かめがまだの AM・G4・Head Chef・Head Chef の印・アカウントの無い事務Crew・社員の表に無い社員 ID のアカウント）、`db/secure-tip-cf-postcheck.sql`（読むだけ・最後に rollback・15 行）。名前・額・中身は出さない。

## 6. 残る限界・次

- **店のタブレット（店舗の PIN）では、Tip の期間の確定を見られない・確定できない、注意ログも見られない**（whoami が店のログインを断る＝v1139 からの決まり）。確定は見られる人が自分の PIN で。
- 事務Crew で、事務Crew のメールのアカウント（manager_auth）に結ばれていない人は、Tip の期間の確定が見えなくなる（① の 9 行目）。
- 確かめていない AM・G4・Head Chef は、注意ログを記録できない（見るのと確定は自分の店と応援の店）。Head Chef の印の無い Head Chef は全店ではなく自分の店（① の 7・8 行目）。
- 本人の成長画面の注意ログの欄（名前の入った警告を全店から探す）は、見られる店の分だけ。G1 などには「このログインでは見られません」と出る。
- 今効いている確定を書き換えられるのは解除できる人だけにしたので、**ほかの端末と同じ期間をほぼ同時に確定すると、あとの端末（解除できない人）が自分の記録で書き換えようとしたときは断られる**（送信待ちに残る。「断られたものを外す」で外せる。この順番の試験は、関数の単体の試験だけ）。
- サーバーは確定の前の業務の確かめ（Tip データのエラー・日次勤怠の承認）をしない（画面だけ。例外承認の印 `forced` は解除できる人だけ）。
- ③ のあと、1146 以前の端末は 2 つの種類を読めず保存できない（送信待ちに残る）。
- ③ の前に公開の鍵で書き換えられていたかは分からない（確定の記録・警告履歴で確かめる）。
- v1144 より前の戻す SQL を v1147 のあとに流すと、2 つの種類もまた公開の鍵で読めるようになる（この一式の戻す SQL を使う）。
