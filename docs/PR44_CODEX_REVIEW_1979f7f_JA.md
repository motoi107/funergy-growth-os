## R1 / P2：遅れて届いた提出結果が別店舗の入力を消す

箇所：`index.html` 17198〜17200 行（`mrSubmit`）。

提出を送る前には `_mr.ed !== ed` を確認しているが、応答後には確認せず `mrEdStop()` と画面の切替を行う。提出中も「戻る」は使えるため、応答待ちの間に別の店を開いて入力すると、前の店の成功応答が新しい店の編集を終了させる。

再現：D6 の提出をサーバーで受け付けた後、応答だけを遅らせる → 戻る → D1 の店長入力を開いて未保存の文字を打つ → D6 の応答を返す。D1 の編集状態が消えて閲覧画面へ移り、文字は DB にも保存されていない。通常の画面操作の関数と本物の API / SQL で確認。

対応：成功応答後も、開始時の編集オブジェクト・店舗・世代が同じか確認し、別の画面の入力や処理中の状態を操作しない。既存の関連テストは「元の編集オブジェクトと違う」だけを確認しているため、`null` に消された場合も通る。新しい編集オブジェクトと文字が残ることを確認する。

## R2 / P2：別タブの未確認の下書きまで一括送信される

箇所：`index.html` 17550〜17553 行、`supabase/migrations/20261012090000_mid_review.sql` 843〜849 行（`mrRpSend` / `mr_reply_send`）。

送信時に照合するのは店長の提出版 `expect_no` だけで、送信する返信の ID・版・集合を送っていない。サーバーはその時点に存在する本人の下書きをすべて送る。同じアカウントの別タブが自動保存した文や追加した下書きも、送信画面に出ていなくても対象になる。

再現：タブ A で相談への返信 1 件を保存 → タブ B でその文を変更し、KPI への返信も追加して保存 → A は元の文 1 件を見たまま「返信する」。エラーなしで B の新しい文と追加の KPI 返信の計 2 件が送信された。提出版の番号は変わっていない。

対応：画面で確認した返信の ID と版を送信要求に含め、ロック中に下書きの集合・版を照合する。食い違う場合は送信せず、入力を残して再読込み・再確認を求める。保存時の版チェックだけでは送信を保護できない。

## R3 / P2：同じ本人の認証更新を別人ログインと判定し、入力を破棄する

箇所：`index.html` 16334 行（`renderMidReview`）。関連：16113〜16115 行（`mrAPI`）、45984 行以降（既存 `invInSessionRefresh`）。

`_mr.sess !== mrSession()` というオブジェクトの比較で、別の人の認証かを判断している。一方、既存の `invInSessionRefresh` は同じ人のトークンを更新するときにも `_botSession` を新しいオブジェクトに置き換える。そのため正常な 401 → 認証更新 → 再試行の後、次の再描画で編集オブジェクト・下書き・開いている店を消す。

再現：D6 の自動保存で一度だけ 401 を返す → 本物の `invInSessionRefresh` で同じ GM の認証を更新 → 再試行の保存は成功 → 「相談がある」の選択で再描画。ログインした本人は変わっていないのに `_mr.ed` と `_mr.view` が `null` になり、直前の未保存の選択も失われた。外部通信はせず、認証サーバーと端末に認証を覚える処理だけを模擬した。

対応：トークンの更新と別人のログインを区別する。検証済みの利用者 ID または同一ログインの更新を追跡し、同じ人の更新では入力を保持する。本当に別人へ切り替わった際の内容消去は維持する。

## R4 / P2：CEO から GM へ変更しても CEO 専用の判断権限が残る

箇所：`supabase/migrations/20261012090000_mid_review.sql` 169〜174 行（`mr_auth`）。関連：`db/mid-review-add-member.sql` の役職確認。

`mr_auth` は `manager_auth` の役職が CEO または GM のどちらかであれば通し、判断に使う役職は初回に写した `mr_members.role` を返す。既存の権限表で CEO → GM に変更しても、中間レビュー側は CEO のまま扱うため、CEO に上がった項目を閉じられる。

再現：架空の CEO を `manager_auth` で GM に変更（`mr_members` の写しは変更しない）→ `whoami` は `ceo` → D3 の CEO 宛て項目へ「対応不要」を送信 → 1 件送信成功、CEO の上位判断が解決済みになった。

対応：少なくとも CEO の決定権限は現在の `manager_auth` でも CEO であることを確認する。役職の不一致を拒否するなど、古い写しで現在の権限を広げない。利用者追加時と役職変更時の扱いもそろえ、上位判断の役職変更試験を追加する。
