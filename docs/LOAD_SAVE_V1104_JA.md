- 依頼：Moto さん 10/21 18:49 HST の添付「Funergy+ 動作・保存障害／LaLa勤怠Jobチェック／Prep専門職スキルマトリクス」の ①。

- 調べた材料：main のコード（v1100 `07f82fe`・v1101 `fb703fc`・v1103 `93ce034`）、`tests/perf/` の模擬サーバー（合成データ・本番の量に合わせたもの）、Chromium（Playwright）。**本番の Supabase・実機（iPhone）・日本の回線では測っていない。** 本番の DB の様子は読むだけの SQL（`db/load-save-1104-check.sql`）で Moto さんに確かめてもらう。

## 1. 原因（確かめたもの）

### 1a. v1101 の「売上・予算の保護」が、使っている端末で止まったままになる（保存できない・最新が取れない・ログインの知らせ）

v1101（10/21 15:07 HST 公開・Codex の PR #88）で、売上（`daily_actuals_<店>`）と予算（`spl_budgets_v2_<店>`）の 10 店 20 キーは、版を照らす保存（`financial_web_commit`）でしか書けなくなった。端末の側では、保護が始まる前の端末の売上・予算を一度「退避」してから、取り込み・保存を許す作り。

- 退避の記録の名前が `_financial_save_recovery_v1`（`_` で始まる）。この名前は「端末の localStorage だけに置く」決まり（`lsIsDeviceLocal`）に当たり、IndexedDB に入らない。
- 使っている端末の localStorage はほぼ満杯（合成データで 4,444,005 文字。Chrome の上限は約 5,242,880 文字）。退避する売上・予算は合わせて約 1,615,033 文字で入らない（`QuotaExceededError`）。
- 退避に失敗すると保護は「退避がまだ」のまま、その画面を閉じるまで（開き直しても同じ）次のことを止める：
  1. ログインの取り込みで、クラウドの新しい売上・予算を端末に書けない（`_lsWriteVerified` が売上・予算のキーを断る）→ 画面は古い売上・予算のまま。「この端末に保存できていない項目が N 件」が出る。
  2. 起動するたびに「売上・予算の最新データを確認できません。元の入力を残して、もう一度確認してください。」（ログインの画面で出る）。
  3. 日次の実績・日報のメモ・予算の入力画面を開くと「最新データを確認できません。通信を確認して、入力画面をもう一度開いてください。」で開かない。
  4. Toast の売上の反映（`syncStoreActualsFromToast`）・天気・予算の保存は、知らせも無く送らずに終わる。
- 当たる端末：一度ログインして売上・予算が端末に入った端末の、2 回目以降の起動（v1100 から更新した端末も、v1101 以降に初めて使った端末も）。店舗・役職の範囲が広いほど（GM・CEO）localStorage が埋まっているので当たりやすい。端末の localStorage に余裕がある端末（見る店が少ない人）は当たらないことがある。
- 模擬環境での再現（`tests/perf/fin-scenario.mjs`・v1100 で使っていた端末を v1103 に更新）：ログインの知らせ・入力画面が開かない・別の端末が保存した売上と予算が画面に出ない・保存できないキー 9 つ。同じ端末を v1104 にすると、すべて直る（5 を参照）。
- 本番：10/21 15:07 HST より後に、売上・予算の行がどれだけ書かれたかは `db/load-save-1104-check.sql` の ② ③ で分かる（書かれていなければ、本番でも保存と Toast の反映が止まっていた）。

### 1b. v1101 の保護が、読むたびに売上・予算を深く写していた（CEO の端末の重さ）

保護は `ls`・`getDailyActuals`・`getBudgets` を包み、読むたびに値を 2〜3 回「1 つ 1 つ形を確かめながら」写していた（`copy`）。CEO のログインからダッシュボードまでに `getDailyActuals` 324 回・`getBudgets` 198 回呼ばれ、この写しだけで約 4 秒（CPU そのまま）。全店を見る CEO がいちばん重い。

## 2. 確かめて、原因ではなかったもの（または小さいもの）

（数字は 4 を参照）
- 日本からの通信の遅さ：往復 200ms・1MB/s にしても、v1100 は 12.0 → 12.8 秒（CPU 4 倍遅く）。重さの主な原因ではない。
- 端末の時間帯（日本）：日付の関数・Toast から取る日付・予算の月は、ハワイ時間のまま（5 を参照）。
- CEO の取得範囲：全店ぶん読むので重いが、v1100 では同じ範囲で 4.6 秒。v1101 の写しで倍になった。

## 3. 直したこと（v1104・アプリだけ・SQL・関数なし）

保護の決まり（版を照らして保存・競合は上書きしない・入力を残す・確認できた保存だけ完了）は変えていない。

1. 退避の記録は IndexedDB だけに置き、1 件ずつ別の名前にする（`financial_save_recovery_v2/` ＋ 書いた時刻と番号）。保護の前の端末の値は別の名前 `financial_pre_guard_archive_v1` に置き、記録には置き場所とキーだけ。どちらも端末だけ（`LS_LOCAL_ONLY`・`LS_LOCAL_ONLY_PREFIX`＝クラウドへ送らない・受け取らない）。localStorage には書かない（満杯のことがあり、古い写しが新しい値の邪魔をする）。
2. 前の名前（v1101〜v1103 の `_financial_save_recovery_v1`・localStorage）の記録は、端末の保存領域を読めるようになったときに 1 回だけ新しい名前へ移し、新しい記録が端末の保存領域に入り終えた（IndexedDB の書き込みが終わった）のを待ってから前の名前を消す。前の記録の中の大きい「保護の前の端末の値」は、記録とは別の名前（`financial_pre_guard_archive_v1`）へ移す。
3. 端末の保存領域（IndexedDB）を読めるまでは、記録を読まない・書かない（その間の localStorage の写しは古いことがある）。その間に断った古い書き込みの退避はメモリに持ち、読めるようになったら記録へ書く（断った値そのものは端末に残っている）。
3a. 保存の前の記録（`pending_request`）は、端末の保存領域に入り終えたのを待ってから送る（押した直後に閉じても残る）。入れられなければ送らない（入力はそのまま・送っていない保存の記録は消す）。
3b. 保存・読み直しの前に、同じ端末のほかのタブが書いた・消した記録を端末の保存領域から読み直す（`_idbReloadPrefix`）。保存はほかのタブと 1 つずつ（`navigator.locks`。無いブラウザーでは今までどおりタブの中だけ）。
4. 読むときの深い写しをやめる：クラウドから読んだ行（確かめて凍結してある）は JSON の文字列を 1 回だけ作って覚え、読むたびにそれを解く（v1100 と同じ「1 回解く」重さ）。予算の「読んだときの姿」は JSON の文字列で、`getBudgets` 1 回につき 1 回だけ。日次の実績では使わないので覚えない。
5. クラウドから読んだ行は 1 行ずつ確かめる（前は 20 行をまとめて確かめ、値の数の上限 20 万・文字の上限 400 万が合計にかかっていた。日次の実績は毎日増えるので、いつか起動の取り込みが毎回失敗する）。

## 3c. 独立レビュー（Claude の別エージェント・作業を見ていない・`4e573bb`）の指摘と直し

指摘（`4e573bb` を書き出したもので、アプリの本物の `_idbQueue`・`_lsStoreGet`・`_lsWriteVerified`・共有の localStorage・タブごとの `_IDB_MEM` で再現）：

- **P1**（タブが 2 つのときだけ）：記録が 1 つの名前で、このタブの写し（`_IDB_MEM`・起動のときに 1 回だけ読む）から読み直して書き直すので、ほかのタブが書いた記録を消していた。例：タブ A が電波の無いところでメモを保存（結果不明・送る前の記録あり）→ タブ B が何か保存 → A を読み込み直すと、送っていないメモが消えている（v1103 は localStorage を毎回読むので残る）。逆に、古いタブが済んだ保存の記録を書き戻すと「保存結果を確認」まで保存が止まる。
- **P2**：保存を押した直後に閉じると、送る前の記録が消える（IndexedDB へは 300ms あとにまとめて書く。localStorage に入っていても、読むときは IndexedDB の古い写しが勝つ）。サーバーに届いていなければ入力が黙って消える。
- **P2**：前の名前の記録を、新しい記録が端末の保存領域に入る前に消していた（満杯の端末で最初の起動中に閉じると、両方なくなる）。
- **P2**（データが増えると）：最初の退避で、全部の行の合計に大きさの上限（値の数 20 万）をかけていた。9 店 × 1,400 日（約 21 万）で止まり、入力画面も開かない（合成データの量で、あと約 1.7〜1.9 年）。
- P3：v1101〜v1103 で退避した端末は、記録の中に約 1.6M 文字の値があり、保存のたびに読み書きする／退避が localStorage に空きがあればそこにも入る／localStorage の古い写しが保存の画面の「未複製」に出る／IndexedDB の無い端末（前から）／`validateRows` の確かめ方（前から・害なし）。
- 問題なしと確かめたもの：読み取りの写しをやめた所（11 通りの比べで、送る中身・出る失敗が v1103 と 1 バイトも違わない）、`getDailyActuals`、読めるまでの扱い、`LS_LOCAL_ONLY`、`_idbBackfill`、移すのをくり返しても同じ。

直し（3 の 1・2・3a・3b と、退避の大きさは全体にかけない）：記録を 1 件ずつの名前にした（足す・消すのはその 1 件だけ＝ほかのタブの記録を消さない）・送る前の記録は書き終わりを待つ・前の名前の記録は新しい記録が入り終えてから消す・最初の退避と `getRecovery` は保存の文字をそのまま使う（合計に上限をかけない）・前の記録の中の大きい値は別の名前へ・済んだ記録もすぐ書き出す。IndexedDB の側に `_idbFlushP`（書き終わりを待つ）・`_idbReloadPrefix`（ほかのタブの書いた・消したものを読み直す）・`financialRecoveryStore`（保護の記録の置き場所）を足した。

試験（`tests/financial-web-save.test.mjs`）：レビューの再現を 6 つ足した（タブ 2 つ・押した直後に閉じる（localStorage に空きがある／満杯）・書けないときは送らない・前の記録を消す順・合計 21 万の値・本物の IndexedDB の関数を fake-indexeddb で）。6 つとも直す前の `a1348be` では落ちる。退避の記録の名前が変わったので、前の試験の「記録の文字」を見る所は 1 件ずつの名前の合計に直した（確かめていることは同じ）。`tests/runtime` に fake-indexeddb 6.2.6 を足した。

## 4. 数字（模擬サーバー・合成データ・Chromium・CEO でログイン → 最初の画面が押せるまで・2 回の値）

端末は「v1100 で一度ログインした端末」の写しを、その版に更新して開いたもの（1 回目＝更新して最初・2 回目＝その後）。v1100 は保護の無い本番（10/21 15:07 HST より前）、v1103・v1104 は保護あり（模擬サーバーも古い書き込みを断る）。

| 条件 | v1100 | v1103（今の本番） | v1104 |

| 近い回線（往復 50ms・5MB/s）・CPU そのまま | 4.7 / 4.6 秒 | 9.3 / 9.0 秒 | 5.2 / 5.1 秒 |
| 近い回線・CPU 4 倍遅く（スマホのつもり） | 12.0 / 12.0 秒 | 34.3 / 33.6 秒 | 14.4 / 14.2 秒 |

- 上の表の v1104 は独立レビューの直しの前（`75f0199`〜`a1348be`）。直したあと（`bc1fdb2`）は、保存と読み直しのたびに IndexedDB の読み直しと書き終わりの待ちが入る。同じ時間に続けて測った比べ（この日の測る機械は上の表の時より遅かった）：近い回線・CPU そのまま 直す前 5.5 / 5.8 秒 → 直したあと 5.9 / 6.0 秒（約 0.2〜0.4 秒増える）・CPU 4 倍 直す前 16.9 / 21.0 秒 → 直したあと 18.5 / 17.0 秒（ばらつきの中）。直したあとも、模擬の場面（メモの保存 → 読み込み直し → 別の端末で見える・答えの届かない保存は 1 回だけ書ける・競合は上書きしない）は同じ結果。

## 5. 確かめたこと（`tests/perf/fin-scenario.mjs`・`tests/perf/tz-check.mjs`・模擬サーバー）

- v1100 で使っていた端末を v1103 にすると：ログインの知らせ・入力画面が開かない・別の端末が保存した売上と予算（F01）が画面に出ない・保存できないキー 9 つ（再現）。
- 同じ端末を v1104 にすると：知らせなし・入力画面が開く・別の端末の売上と予算が出る・保存できないキーなし・Toast の売上の保存も通る（状態 committed）。
- 日報のメモを保存 → クラウドの行の版が進み、メモが入る → 読み込み直しても残る → 別の端末（GM・v1104）でログインするとそのメモが見える。
- 保存の答えだけが届かない（サーバーには書けた）：「保存結果がまだ確認できていません」の帯・入力は残る →「保存結果を確認」で committed・サーバーへの保存は 1 回だけ（二重にならない）。
- 入力画面を開いたあとで別の端末が同じ店の売上を保存：上書きしない・入力は残る（「ほかの画面で更新されています」）→ 開き直して保存すると、自分のメモが入り、別の端末の売上も残る。
- 端末の時間帯が日本（10/22 14:49 JST＝10/21 19:49 HST）：`bizToday` は 2026-10-21・Toast に頼む営業日は 20261021・予算の月は 2026-10（ハワイ時間と同じ）。
- 更新していない端末（v1100）は、保護のある本番では売上・日報・予算を保存できない（端末には残るが、クラウドの行は変わらない・知らせも出ない）。→ 全員の端末を v1104 に。
- 試験：`tests/financial-web-*.test.mjs` 58（v1101 の 53 ＋ v1104 の 5。v1104 のうち 2 つは v1103 のコードで落ちる）・static release pass（1104）・全体（重いもの以外）の失敗は main と同じ。
