# v1107：答えが確かめられない保存 1 件で、売上・予算の読み込みと保存がすべて止まる不具合

## 1. 報告（Moto さん 10/24 08:37 HST・本番 v1106・iPhone の写真）

- ダッシュボードの上の帯：「売上：取れませんでした（TT・TK・T-K ほか4店）。前回 10/23 14:25 の情報を表示中」「予算：取れませんでした。前回 08:33 の情報を表示中」「勤怠 08:36 取得」。
- 画面の下の黄色い帯：「保存結果がまだ確認できていません。同じ保存の結果を確認してください。」［保存結果を確認］［同じ内容で再送］。
- 08:55 HST：ボタンを押しても何も変わらない。以前は普通に使えていた。
- 08:59 HST：Moto さんが流した SQL（読むだけ）の結果：`anon` の `statement_timeout=3s`・`authenticated` 8s・`authenticator` 8s と `lock_timeout=8s`。

## 2. 原因（コードと模擬サーバーで確かめた範囲）

- v1101（PR #88・Codex）の売上・予算の保護は、保存の答えが確かめられない保存（`pending`・状態 unknown）が 1 件でもあると、それが片づくまで **売上・予算の読み込み（`refresh`）と保存（`perform`）をすべて断る**（`financial_unresolved_save`）。記録は端末に残るので、読み込み直しても続く。
- ログインの同期は全店の Toast の売上を保護に渡して 1 店ずつ保存する。1 店の保存がサーバーのエラー（下）で返ると、その店が unknown のまま残り、**残りの店の取り込みも予算の読み込みも断られる**＝写真の帯そのもの。
- 押しても片づかない：保護は unknown から抜ける道を 2 つしか持たない（受け取りが「済み」、または送り直しが「重なった」）。サーバーが同じ保存を毎回エラーで返すと（受け取りは「届いていない」・送り直しはまたエラー）、どちらにも行かず、ずっと止まる。自動で確かめ直すこともしなかった。
- サーバーのエラーの第一候補：保存の関数 `financial_web_commit` はアプリの鍵（anon）で呼ばれ、**3 秒の上限**（`statement_timeout=3s`）がある。3 秒を超えるとサーバーが途中で取り消し、HTTP 500・`57014` を返す。アプリはこれを「答えが確かめられない」と扱っていた（`40001 financial_guard_version_conflict` 以外のエラーはすべて unknown）。3 秒を超える理由（同じ時間に何台もの端末が同じ店の行を保存して待たされる・行が大きい・見張りの trigger など）は、関数の中身と行の大きさを見ないと分からない（`db/financial-save-1107-check.sql` の結果待ち）。
- 「以前は使えていた」：ふだんは 3 秒以内に答えが返るので表に出ていなかった。1 回でも超えると、その端末は止まったままになる作り（v1101 から）。

模擬サーバー（`tests/perf/mock-api.mjs` に 500・57014 を返す口 `/__fin_fail`、Toast の売上を変える口 `/__toast_bump` を足した）で、本番の v1106 を GM でログインさせ、F01 の保存だけをエラーにすると、写真と同じ帯（「売上：取れませんでした（TT・TK・T-K ほか4店）」・予算も取れない・黄色い帯）になり、ほかの 6 店にも何も書かれないことを確かめた（`tests/perf/fin-stuck.mjs`）。

## 3. 直したこと（アプリだけ・index.html と sw.js。SQL・関数・データベースの設定は変えていない）

保護の決まり（版を照らす・重なったら上書きしない・人の入力は確かめられた保存だけを完了にする・同じ番号の保存は 1 回しか書かれない）は変えていない。

1. **自動の保存は止めない**：人が入力していない保存（`AUTO_SOURCES`＝Toast の売上の取り込み・期間の取り込み・天気・予算の印の移し替え）は、
   - 送った答えが確かめられなければ、届いたかを 1 回だけ確かめる（受け取りが「済み」ならそのまま完了）。
   - 届いていない・重なった・確かめられないときは **放す**（`release`）：その店は「取れませんでした」にして、ほかの店・予算の読み込みと保存を続ける。その店は帯の自動のやり直し（15・30・60 秒）か［売上をもう一度］で最新を読み直して送り直す（前の番号は使わない）。
   - 記録には小さな印（`auto_released`・30 件まで）だけを残し、行の中身は残さない（人の入力ではないため）。放した保存がサーバーで遅れて書けても、次の保存は版を照らすので上書きしない。
   - 前は「重なった」ときも黄色い帯で止めていた（`background conflict … never automatically retries` の試験）。今は放す（送り直しはしない・上書きもしない）。試験を書き直した。
2. **人の保存は押さなくても確かめる**：答えが確かめられない人の保存は、2 秒・10 秒・30 秒・1 分・2 分・5 分…で受け取りを確かめ、「届いていない」と分かれば同じ内容（同じ番号）で送り直す。画面に戻ったとき・通信が戻ったときはすぐ確かめる。
3. **抜け出す道**：サーバーが受け取りに答えたのに片づかない人の保存（「届いていない」のに送り直してもサーバーがエラー／サーバーの答えをこのアプリが受け取れない形）には、帯に［保存をやめて入力を保管］を出す（確かめの画面のあと）。入力は端末の記録（`abandoned_unconfirmed`）に残し、画面の売上・予算はサーバーの最新を読み直す。届いたか分からないあいだ（通信が切れている）は出さない。
4. **前の版の記録**：v1101〜v1106 の記録にはどの保存かの印が無い。変わった所が Toast の売上・天気の欄だけ（予算は合計 `actual` と保存の時刻 `_ts` だけ）なら自動の取り込みと見分けて放す（記録は消さずに残す）。人の入力（日次の実績・メモ・予算）は入れた人・時刻の欄（`by`・`at`・`_at` など）も変わるので当たらない（試験で確かめた）。**本番で止まっている端末は、v1107 に更新して開くだけで帯が消える見込み**（模擬サーバーで v1106 の止まった端末を v1107 で開いて確かめた）。
5. **理由を出す**：黄色い帯に「理由：サーバーのエラー（HTTP 500・57014）」など（`why`）と「この保存が片づくまで、売上・予算の読み込みと保存を止めています」。上の帯の「取れませんでした」にも理由（例「理由：サーバーのエラー（HTTP 500・57014）」「下の黄色い帯の保存を先に確かめてください」）。
6. **片づいたらすぐ取り直す**：黄色い帯が片づいたら、取れなかった売上・予算を 1 秒後に取り直す（`onState` → `fstOnGuardState`。ログインの同期の途中はいつもの間隔）。

## 5. 残ること・限界

- **3 秒を超える原因はまだ直していない**（サーバー）。v1107 では、超えた店だけが「取れませんでした（理由）」になり、ほかは止まらない。同じ店がずっと超えるなら、関数の中身・行の大きさ（`db/financial-save-1107-check.sql`）を見て、サーバー側をどうするか Moto さん・Codex と決める（データベースの設定は勝手に変えない）。
- 人の保存が答えの無いまま（通信が切れている）だと、片づくまで読み込みと保存は止めたまま（今までどおり）。自動で確かめ続ける。
- 実機（iPhone・日本の端末）では確かめていない。模擬サーバーとChromium（390px）だけ。
- 独立レビューは無し（急ぎ）。Codex のレビューはまだ。
