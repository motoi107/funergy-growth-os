# Funergy＋業務Bot

経理センター → 業務Bot。管理者メール認証後に共有案件を表示。既存の管理者用画面にも同じBotタブを置く。取得済みデータのローカル下書きは既存判定を直接使用する。

## 実装と運用

- ops-bot Edge Function。通常操作はSupabase Authのユーザー確認と既存manager_authの役割で認可。PINやクライアントのroleだけでは共有データを返さない。
- bot_* テーブルのみへ保存。RLSと権限剥奪でanon/authenticatedの直接アクセスを拒否。service-only SECURITY INVOKER RPCで案件更新と監査記録を同一トランザクションにする。
- LINE受信は生の本文バイトでHMAC署名検証。受信イベントIDで重複を防ぐ。未知グループはIDのみ登録し、会話は取り込まない。GM/CEOが店舗へ紐付けたグループで、先頭「発注依頼」「/order」「order request」のテキスト、またはB-…案件番号付き返信だけを取り込む。画像・音声・一般会話の自動理解は含まない。
- 修正返信はverifyへ移動し、完了にはしない。Toast GUIDを直接取得し、既存判定、同一従業員の同日の新しい打刻、重複、手動補正を照合。移動・削除・欠落・未退勤・異常継続は自動完了しない。経理の確認による完了は理由必須で別イベント。
- LINE送信はGM/CEO/経理が宛先と本文を確認して押したときだけ。outboxとX-Line-Retry-Keyで不明結果の再確認を同じ送信として行う。23時間超過や結果不明はLINE履歴で人が確認し、記録して解除。送信受付は既読・配達確認とは異なる。
- 発注依頼には商品ページURLと数量を保存し、権限者が承認。商品ページへ移動し、人が注文後に注文番号を記録する。Amazonカート作成・自動注文は未対応（Amazonアカウント/連携方式は経理確認待ち）。
- 新規Toast取得は既存hyper-workerと集計テーブルを変更しない。時刻判定は生成コピー。Toast直接取得では従業員GUIDで集約し、氏名の部分一致はしない。これにより既存画面の名寄せ結果とは異なる場合がある。時間クリップ・Tip分割はshifts自体を変更しないことをソースで確認した。手動補正は削除せず警告し、自動完了を止める。端末内の未同期補正までサーバーから確認できる保証はない。
- 勤務中の可能性を残す未退勤は「勤務継続か打刻漏れか確認」として案件化。退勤漏れと断定しない。既存の確実/疑い判定・12時間・Hawaii -10h・判定順序は維持。
- 全体のclock設定はGM/CEOが既存の設定を確認して初回適用する。公開後はアプリも同じ設定を読み、変更は認証してサーバーへ保存後に反映。匿名経路に公開するのはこの4設定だけ。
- 自動取得は初期OFF。GM/CEOが有効にすると毎日08:40から店舗を1分ずらして前営業日の勤怠/Voidを取得し、修正報告済み勤怠を最大10件/店で再確認。トークンはDBのservice-only設定で保持し、cronから参照。自動送信はない。店舗追加時はschedule SQL再適用が必要。
- 一覧は最新200案件、案件履歴は最新100イベント。古いデータは削除しない。

## LINE接続の残る手作業

SupabaseのEdge Functions → SecretsへLINE_CHANNEL_SECRETとLINE_CHANNEL_ACCESS_TOKENを設定する。既に画面で共有されたChannel secretは再発行した値を使用。チャット、公開リポジトリ、ブラウザコードへ値を書かない。

Webhook URL:
https://tgbhgxzehzeouopklhje.supabase.co/functions/v1/ops-bot?route=line

LINE Developersで上記URLを設定し、Webhook検証、Webhook利用、再送を有効にする。テストグループにBotを追加し、Funergy＋でグループを店舗に紐付ける。接続情報の存在だけでは、Webhook設定や配達成功の証拠にはならない。

## 全店共通グループと担当者（1004）

本部全員と各店舗マネージャーの共通LINEグループは、グループ設定で「全店舗」を選ぶ。既存の単店舗グループは範囲を維持する。受信済みグループを押すと入力欄へ取り込める。グループ名・範囲・有効チェックを保存してから使う。

「店舗の担当者設定」で新規案件の担当者名を登録し、個別案件で変更できる。変更履歴と競合チェックを保持。未設定は店舗マネージャーと表示。送信には案件番号・店舗名/ID・担当者名をサーバーで付加し、確認ダイアログにも表示する。担当者名は本文表示であり、LINEの@メンションや個人IDの照合は未実装。グループ内の他の担当者からの代理報告も履歴に残し、報告者が担当者本人だとは断定しない。

報告は `B-案件番号 完了` または `B-案件番号 done`。修正済み・対応済み等も番号直後なら受け付ける。否定文・質問や一般会話から完了を推測しない。完了報告はverify（再確認待ち）まで。勤怠は既存のToast照合、Voidは経理の確認、発注は承認・注文番号の既存フローを維持。取得と報告処理が自動でも、グループへの送信は引き続き担当者の確認操作が必要。

全店グループの発注は `発注依頼 [店舗名またはID] 商品名`。店舗名は登録名との完全一致（大小文字は無視）、一意でない場合も自動選択しない。指定がなければ本文を保留一覧に保存し、経理が店舗を選んで案件化。元イベントをロックし、二重操作や再送でも1件だけ作る。最新画面では未割当を古い順50件まで表示する。

適用順: db/ops-bot-all-stores.sql → ops-bot → APP_VERSION/SW_BUILD 1004。既存グループを自動で全店化・有効化しない。更新後に対象を選んで設定する。新しいDB関数もservice-only。実LINEへの送信・本番テスト案件作成は実施しない。

## 勤怠・決済Void・未決済の監視（1005）

初期一覧と通常取得は勤怠。「決済Void・未決済」から指定日の会計データを追加取得する。商品・モディファイア、注文全体/会計全体だけの取消は対象外。既存案件と履歴は削除せず、対象外Voidは通常一覧・送信から除外する。

日次の新規取得は勤怠が基本。GM/CEOが決済Void・未決済の自動取得を別途有効にできる。決済VoidはvoidBusinessDateで取消日に発生した決済を取得し、元注文が過去日でも参照する。未決済は対象営業日のOPENで金額が正の会計。過去の全営業日を自動遡及する機能はなく、運用開始時に必要な日付を取得する。1日の決済Voidが100件を超える場合は取得をエラーにして手動確認を要する。通信失敗も全件取得成功として扱わない。

自動取得を有効にすると、未解決の勤怠・決済Void・未決済を毎時、店舗ごとに時刻をずらして再確認する。確認が古いものから最大20件/店/回、45秒の実行予算で開始を制限する。件数・応答時間により一巡は1時間以上かかる。取得失敗・照合不可は未解決に残し、最終確認時刻と理由を保存する。

LINE完了報告は再確認待ち。勤怠は既存判定とGUID照合、未決済は元会計のCLOSED・金額不変・回収額充足、決済Voidは元決済の存在と元会計の金額不変・代替回収を確認して完了にする。カードのAUTHORIZEDだけでは回収済みにしない。削除・取消・金額変更・証拠不足は自動完了せず、権限者が理由を記録して確認する。正常な取消など、人による確認を要する案件は残る。

LINE通知は経理等が宛先と本文を確認して送信する。自動送信・再通知は未実装。監視の対象は検知・登録された案件であり、Toast全履歴の全異常を取得済みとはみなさない。解決済み未決済が再びOPENで取得された場合は案件を再開する。

適用順: db/ops-bot-monitor.sql → ops-bot → db/ops-bot-schedule.sql → APP_VERSION/SW_BUILD 1005。既存の認証・権限・注文承認を維持。
