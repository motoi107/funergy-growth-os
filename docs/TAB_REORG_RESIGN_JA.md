## 8. 退職完了の不具合：原因（v1085・コードと合成データで確かめた）

- 従業員の表（Supabase の `employees`）は、端末が保存するたびに **全員分を丸ごと** 書いていた（`lsSet('m_employees')` → `syncMasterToSupabase` → upsert の merge-duplicates＝行ごと上書き）。退職の前から開いていた端末（店舗のタブレット・開いたままの PWA）が、ほかの人を直す・オンボーディングのチェック・OJT の Prep・昇格の承認などで保存すると、退職した人を「在籍」のまま書き戻していた。次にログインした端末はクラウドの表で丸ごと置き換えるので、どの端末でも在籍に戻って見えた。
- 取り込み（ログイン・「最新に更新」）は端末の表を丸ごと置き換えた。電波の無いところで退職にした変更は、送れる前の取り込みで消えた（未送信の再送も、置き換えたあとの表を送る）。
- ほかにも戻る道があった：退職記録（offboardings）の合流は「手元が勝つ」で、完了の前から開いていた端末がチェックを 1 つ直すと「完了」が「進行中」に戻った／オンボーディングの「Crew化」は名前で探し、同じ名前の退職者を在籍に戻した／従業員の編集画面・「休職にする」のボタンで退職から外せた／完了した退職手続きの承認を取り消すと在籍に戻った。
- 「退職手続きを完了」は退職記録に「完了」を書くだけで、従業員の状態・ログインを確かめていなかった（前の画面の操作で退職にしてあった前提）。
- サーバー：ログインの PIN の照合（auth-pin）は、退職した人でも PIN が合えば通した（印を出さないだけ）。Toast 取込（hyper-worker）はログインの印の人が退職かを見ていなかった。管理者のメールのアカウント（manager_auth）は退職しても役割が残った（Invoice取込・業務Bot・PIN 一覧・中間レビューの GM・CEO）。
- 合成データの試験で、v1084 のコードのまま 2 つとも再現した（`tests/employee-resign-sync.test.mjs` の最初の 2 つ：古い端末の保存で在籍に戻る・電波の無い退職が取り込みで消える）。

## 9. 直し：アプリ v1085

- 従業員の表は「この保存で変えた人の、変えた欄」だけを覚えて送る（未送信の印 `emp_dirty_q`。localStorage がいっぱいなら IndexedDB に、それもできなければメモリに持ってすぐ送る。どれもだめなら保存できなかったと出す）。画面が読んだときの表（`getEmployees` の `__src`）と比べるので、そのあいだに取り込んだほかの人・ほかの欄は戻さない。送るときはその人のクラウドの最新を読み、変えた欄だけを重ねて送り、読み直して入ったかを確かめる。給与・メール・電話は今までどおり公開の表に書かない。「マスター一括投入」は、クラウドに無い人だけ足す。
- 状態（status・resignDate・osDisabled）を変えたときは、画面が読んだときの版（`_stV`）を付けて送る。サーバーは版が同じときだけ通す。通らなければ「ほかの端末で先に変わっていました」と出して、クラウドの状態にする。取り込みは、端末の版のほうが新しい人の状態を古いクラウドの状態で戻さない（版は上がるだけ）。
- サーバーが受け付けない行（400 など）は 1 行ずつ送り直し、ほかの人の変更を止めない。その行には印を付けて知らせ、直すまで送らない。アプリの起動中の 1 回だけの直しと、取り消した昇格（ghTxn のロールバック）は送らない。
- 退職手続きを完了：⓪ 退職記録をサーバーで読み直す（ほかの端末で「取消」なら完了しない）① サーバーのいまの版の上で、退職・最終出勤日・OS アカウント無効に（済んでいれば何もしない）② ログイン（PIN・紐づく管理者のアカウント）が止まったかをサーバーで確かめる（`employee_access_state`。止まっていなければ止め直す。SQL が入っていなければ完了しない）③ 同じ名前の人が在籍していると PIN を名前で止められないので、聞いてから記録に残す（`pinShared`）④ 退職記録を「完了」にして送る（送れなければ完了に戻さない）⑤ もう一度読み直し、そのあいだに取消になっていたら知らせる。どこかで失敗したら完了にせず理由を出す（もう一度押せば続きから。繰り返しても壊れない）。完了の日時・実行者は今までどおり記録に残り、状態を変えた時刻と人（`_stAt`・`_stBy`）とサーバーの記録（`employee_status_log`）も残る。
- 在籍に戻すのは従業員マスターの「在籍に戻す」だけ。サーバー（auth-pin v1085 の restore）がメールで認証した CEO・GM・AM・経理（manager_auth に登録され、紐づく社員が在籍の人）かを確かめて、状態・PIN・管理者のアカウント・業務Bot を戻し、その人の退職記録を「取消」にする。端末は先に書かない（失敗したら何も変わらず、あとで送られることもない）。PIN のログインだけでは戻せない（初めて押すとメールの認証を聞く）。
- 退職の承認の取り消し：退職記録をサーバーで読み直し、「完了」「取消」なら断る。退職になっていればサーバーで在籍に戻し（記録は取消にしない）、記録を「申請中」・世代（`_gen`）を上げて送る。
- 編集画面・「休職にする」などのボタン・オンボーディングでは、退職した人を在籍に戻さない。編集画面は開いたときの表と比べ、変えた欄だけを保存する。オンボーディングは登録した社員 ID で探し、同じ名前の退職者がいるときの登録は止める（新しい ID で作り直さない）。
- 退職記録の合流：完了・取消は終わり（取消 ＞ 完了）。それまでは世代（承認の取り消しで上がる）→ 申請中 ＜ 進行中・却下 → 新しい時刻の順。中身（チェック・清算）は新しい更新。サーバーも app_state の見張りで、古い写しが完了・取消を戻す・消すのを止める。
- ログイン中の端末：開いたとき・前面に戻ったとき・電波が戻ったとき・5 分ごとに、サーバーでその人を確かめる（メールでログインした人はそのアカウントの社員 ID で）。サーバーが在籍なら、端末の古い「退職」でログアウトしない（端末を直す）。サーバーに届かないときは端末の状態で（ログインのときは止める側）。退職・停止なら、メモリの PIN・ログインの印、その端末に覚えたメール認証を消してログアウト。
- 一覧・検索・選ぶ候補は今までどおり退職を外す（在籍のタブ・ログインの名簿・シフトなど）。退職のタブには残る。物理削除はしない（過去の勤怠・給与・チップ・評価の記録と参照はそのまま）。PIN 一覧で止めた PIN は「停止中」と出す。

## 10. サーバー（SQL 20261023090000・関数 2 つ）

- SQL（`supabase/migrations/20261023090000_employee_resign_guard.sql`・入れる一式 `deploy/employee-resign-v1085/`）：
  - `employees` に見張り（トリガー）。状態を変える書き込みは、送られてきた版がいまの版と同じときだけ通し、版を進める（サーバーの時刻を `_stAt` に）。古い写しの書き込みは状態だけ今のまま残し、ほかの欄は書く（前の版のアプリにも効く）。列の status だけを変えた書き込みも同じに扱う。入れたときに、いまの行すべてに版 1 を付ける（入れる前に退職・休職にした人も守る）。
  - **在籍に戻す（止めた状態から外れる・退職から外れる）のは、サーバー（service_role＝auth-pin）と SQL Editor（データベースの持ち主）だけ。** アプリの鍵では、いまの版を付けても通さない（`refused` と記録）。`_restoreAt`・`_restoreBy` もサーバーだけが書く。
  - `employee_restore(社員ID, 戻した人, 承認の取り消しか)`：service_role・SQL Editor だけ。在籍・OS 有効・`_restoreAt`／`_restoreBy` にし、その人の退職記録（app_state）を「取消」にする（承認の取り消しのときはしない）。2 回呼んでも同じ。
  - 退職・OS アカウント無効になったら：その人の PIN を止める（印 `!blocked`・前の PIN は `employee_access_hold` に残す。同じ名前の在籍者がいるときは止めない）・紐づく管理者のメールのアカウント（`manager_auth.emp_id`）の役割を `suspended` に・同じアカウントの業務Bot（`bot_users`）を止める。在籍に戻すと元に戻す。あとから同じ名前の人が入ったら、その名前は初期の PIN に（退職した人の PIN は渡さない）。名前を変えたら止める名前も移す。

## 11. アクセスを止める対象と、ログイン中の端末

| 入口 | 退職・停止のあと |
|---|---|
| PIN のログイン（名簿・auth-pin） | 名簿に出ない。PIN が合っても断る（「このアカウントは使えません（退職・停止中）」）。SQL で PIN も止める |
| ログイン中の端末（アプリ v1085） | 開いたとき・前面に戻ったとき・電波が戻ったとき・5 分ごとにサーバーで確かめてログアウト。メモリの PIN・ログインの印、その端末に覚えたメール認証（Invoice取込・業務Bot）を消す |
| ログインの印（14 日）で Toast 取込 | hyper-worker v1085 が断る |
| 管理者のメールのアカウント（紐づく社員がいる） | 役割 `suspended`：管理者ページ・Invoice取込・業務Bot・PIN 一覧・中間レビューの GM・CEO・在籍に戻すで断られる。中間レビューの AM・Head Chef・入力担当は前から退職を断る |
| 業務Bot だけのアカウント（`bot_users`） | 同じアカウントが manager_auth で社員に紐づいていれば止まる。紐づいていないものは止まらない（1_確かめで一覧） |
| 店舗のアカウント（共有の店舗PIN） | 社員に結びつかないので止めない（他の人の運用を止めない）。店舗PIN を知っていた人なら店舗PIN を変える |

- 限界（変えていない）：アプリの公開の鍵（anon）で読み書きできる表（`app_state`・`employees` など）は、鍵を知っていれば誰でも読み書きできる（前からの作り）。v1085 で、在籍に戻すことと PIN・アカウントの停止の解除はサーバーだけにしたが、ほかの書き込みは止めていない。止めるには、ログインした人ごとの権限（RLS）に作り替える大きな作業が要る（バックログ）。
