## 8. 退職完了の不具合：原因（v1085・コードと合成データで確かめた）

- 従業員の表（Supabase の `employees`）は、端末が保存するたびに **全員分を丸ごと** 書いていた（`lsSet('m_employees')` → `syncMasterToSupabase` → upsert の merge-duplicates＝行ごと上書き）。退職の前から開いていた端末（店舗のタブレット・開いたままの PWA）が、ほかの人を直す・オンボーディングのチェック・OJT の Prep・昇格の承認などで保存すると、退職した人を「在籍」のまま書き戻していた。次にログインした端末はクラウドの表で丸ごと置き換えるので、どの端末でも在籍に戻って見えた。
- 取り込み（ログイン・「最新に更新」）は端末の表を丸ごと置き換えた。電波の無いところで退職にした変更は、送れる前の取り込みで消えた（未送信の再送も、置き換えたあとの表を送る）。
- ほかにも戻る道があった：退職記録（offboardings）の合流は「手元が勝つ」で、完了の前から開いていた端末がチェックを 1 つ直すと「完了」が「進行中」に戻った／オンボーディングの「Crew化」は名前で探し、同じ名前の退職者を在籍に戻した／従業員の編集画面・「休職にする」のボタンで退職から外せた／完了した退職手続きの承認を取り消すと在籍に戻った。
- 「退職手続きを完了」は退職記録に「完了」を書くだけで、従業員の状態・ログインを確かめていなかった（前の画面の操作で退職にしてあった前提）。
- サーバー：ログインの PIN の照合（auth-pin）は、退職した人でも PIN が合えば通した（印を出さないだけ）。Toast 取込（hyper-worker）はログインの印の人が退職かを見ていなかった。管理者のメールのアカウント（manager_auth）は退職しても役割が残った（Invoice取込・業務Bot・PIN 一覧・中間レビューの GM・CEO）。
- 合成データの試験で、v1084 のコードのまま 2 つとも再現した（`tests/employee-resign-sync.test.mjs` の最初の 2 つ：古い端末の保存で在籍に戻る・電波の無い退職が取り込みで消える）。

## 9. 直し：アプリ v1085

- 従業員の表は「この保存で変えた人の、変えた欄」だけを覚えて送る（端末だけの `_emp_dirty`）。画面が読んだときの表（`getEmployees` の `__src`）と比べるので、そのあいだに取り込んだほかの人・ほかの欄は戻さない。送るときはその人のクラウドの最新を読み、変えた欄だけを重ねて送り、読み直して入ったかを確かめる。取り込みは送れていない変更を残して重ねる。給与・メール・電話は今までどおり公開の表に書かない。「マスター一括投入」は、クラウドに無い人だけ足す。
- 状態（status・resignDate・osDisabled）を変えたときは、読んだときの版（`_stV`）を付けて送る。サーバーは版が同じときだけ通す。通らなければ「ほかの端末で先に変わっていました」と出して、クラウドの状態にする。
- 退職手続きを完了：① 従業員を退職・最終出勤日・OS アカウント無効に（済んでいれば何もしない）② サーバーに入って、ログイン（PIN・紐づく管理者のアカウント）が止まったかを確かめる（`employee_access_state`。止まっていなければ止め直す）③ 退職記録を「完了」にして送る。どこかで失敗したら完了にせず理由を出す（もう一度押せば続きから。同じことを繰り返しても壊れない）。完了の日時・実行者は今までどおり記録に残り、状態を変えた時刻と人（`_stAt`・`_stBy`）とサーバーの記録（`employee_status_log`）も残る。
- 在籍に戻すのは従業員マスターの「在籍に戻す」（CEO・GM・AM・経理・前と同じ）だけ。サーバーに入ったのを確かめてから退職記録を「取消」にする。編集画面・「休職にする」などのボタン・オンボーディングでは戻さない。完了した退職手続きの承認は取り消せない。同じ名前の退職者がいるときのオンボーディングの登録は止める（新しい ID で作り直さない）。オンボーディングは登録した社員 ID で探す。
- 退職記録の合流：状態は 申請中 → 進行中 → 完了（取消・却下は終わり）と前へだけ進む。承認を取り消して申請中に戻すときは世代（`_gen`）を上げる。中身（チェック・清算）は新しい更新。
- 一覧・検索・選ぶ候補は今までどおり退職を外す（在籍のタブ・ログインの名簿・シフトなど）。退職のタブには残る。物理削除はしない（過去の勤怠・給与・チップ・評価の記録と参照はそのまま）。
- PIN 一覧で止めた PIN は「停止中」と出す。

## 10. サーバー（SQL 20261023090000・関数 2 つ）

- SQL（`supabase/migrations/20261023090000_employee_resign_guard.sql`・入れる一式 `deploy/employee-resign-v1085/`）：
  - `employees` に見張り（トリガー）。状態を変える書き込みは、送られてきた版がいまの版と同じときだけ通し、版を進める（サーバーの時刻を `_stAt` に）。古い写しの書き込みは状態だけ今のまま残し、ほかの欄は書く（前の版のアプリにも効く）。入れたときに、いまの行すべてに版 1 を付ける（入れる前に退職した人も守る）。
  - 退職・OS アカウント無効になったら：その人の PIN を止める（印 `!blocked`・前の PIN は `employee_access_hold` に残す。同じ名前の在籍者がいるときは止めない）・紐づく管理者のメールのアカウント（`manager_auth.emp_id`）の役割を `suspended` に・同じアカウントの業務Bot（`bot_users`）を止める。在籍に戻すと元に戻す。
  - `employee_access_state(社員ID, 直す)`：アプリの鍵で呼べる（返すのは止まっているかどうかだけ）。記録 `employee_status_log`・前の値 `employee_access_hold` はサーバーだけ。
  - 確かめ（読むだけ）`db/employee-resign-check.sql`・確認 `db/employee-resign-postcheck.sql`・既に退職の人に適用 `db/employee-resign-apply-existing.sql`・戻す `db/employee-resign-rollback.sql`。
- auth-pin v1085・hyper-worker v1085：ソースは公開しない（Moto さんに直接渡した）。auth-pin は退職・停止の人の PIN の照合と本人の PIN の変更を断る（社員 ID で・無ければ名前で）、ログインの印に社員 ID、PIN 一覧・リセットは紐づく社員が退職なら断る。hyper-worker は個人のログインの印の人が退職・停止なら断る。

## 11. アクセスを止める対象と、ログイン中の端末

| 入口 | 退職・停止のあと |
|---|---|
| PIN のログイン（名簿・auth-pin） | 名簿に出ない。PIN が合っても断る（「このアカウントは使えません（退職・停止中）」）。SQL で PIN も止める |
| ログイン中の端末（アプリ v1085） | 開いたとき・前面に戻ったとき・電波が戻ったとき・5 分ごとに確かめてログアウト。メモリの PIN・ログインの印、その端末に覚えたメール認証（Invoice取込・業務Bot）を消す |
| ログインの印（14 日）で Toast 取込 | hyper-worker v1085 が断る |
| 管理者のメールのアカウント（紐づく社員がいる） | 役割 `suspended`：管理者ページ・Invoice取込・業務Bot・PIN 一覧・中間レビューの GM・CEO で断られる。中間レビューの AM・Head Chef・入力担当は前から退職を断る |
| 業務Bot だけのアカウント（`bot_users`） | 同じアカウントが manager_auth で社員に紐づいていれば止まる。紐づいていないものは止まらない（1_確かめで一覧） |
| 店舗のアカウント（共有の店舗PIN） | 社員に結びつかないので止めない（他の人の運用を止めない）。店舗PIN を知っていた人なら店舗PIN を変える |

- 限界（変えていない）：アプリの公開の鍵（anon）で読める表（`app_state`・`employees` など）は、鍵を知っていれば誰でも読める（前からの作り）。退職者がその鍵で直接読むことは止められない。止めるには、ログインした人ごとの権限（RLS）に作り替える大きな作業が要る。
- emp-private・ob-private・discount-log・drive-sync などのソースは手元に無く、確かめていない。PIN で照合する関数が auth_pins の PIN を見ているなら、PIN を止めたことで断られる（未確認）。メールのアカウントの役割を見ている関数は `suspended` で断られるはず（未確認）。

## 12. 既にある退職者のデータの修復

- 確かな記録があるのは「退職手続きが完了（offboardings の `完了`）なのに在籍になっている人」だけ。`db/employee-resign-check.sql` で数と名前が分かり、アプリの従業員マスター（GM・CEO）の「退職の記録と食い違う人」で 1 人ずつ「退職に戻す」か「在籍のまま（再入社など）」を選ぶ。記録の無い人は出さない（推測で退職にしない）。入社日が完了より後の人には「再入社かもしれません」と出す。
- 退職記録そのものが「進行中」に戻されていた人は、完了の記録が残っていないので出ない（分からない）。
